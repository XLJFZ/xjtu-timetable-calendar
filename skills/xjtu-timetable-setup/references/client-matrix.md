# 怎么选订阅客户端（决策版）

矩阵全表在 README。这里只回答"用户提了这个诉求，该选哪条路、为什么"。

## 「我要它自己更新」

必须是**订阅型**入口。分辨方法很简单：订阅型入口带「上次同步时间」，
导入型只有显示开关。

- **Google 日历**：只有**网页版**能订阅（左侧「其他日历 → 通过 URL 创建」）。
  手机 App 里既没有订阅入口，也**不显示** URL 导入型日历——别在 App 里找。
- **Outlook.com**：网页版「添加日历 → 订阅日历」，但对话框会强制你手填日历名，
  产物里的 `X-WR-CALNAME` 它不采用。
- **ColorOS 系统日历**：自带「URL 日历」订阅入口（我的 → 添加日历 → URL 日历），
  会定期回源并**原地更新**已存在的事件，日历名直接采用 `X-WR-CALNAME`。
- **其他国产 ROM**：用 ICSx⁵ 做 URL 订阅。注意是 **ICSx⁵**，不是 DAVx⁵
  （后者只做 CalDAV，没有 URL 订阅入口）。给同步器关掉电池优化并允许自启动，
  否则后台查杀会伪装成"装了但不更新"。
- **Apple 日历（iOS / macOS）**：走订阅入口，别双击导入。可以**试** CLI 四处打印的那条
  `webcal://` 链接（只是把 `https://` 换个 scheme，指向同一份 `.ics`）；「点开即弹订阅确认」
  **未在本项目真机验证**，只能说「通常」，失败就手动：iOS「设置 → 日历 → 账户 → 添加账户 →
  其他 → 添加已订阅的日历」、macOS「文件 → 新建订阅日历」。它**不改变发布物形态** ——
  tip 上仍然只有一个 `<token>.ics`，不要为此多发一个 `.webcal` 文件。
- **一次性导入**（Apple 日历双击 .ics、各家"导入日历"入口）：一次性快照，
  之后 push 多少次都收不到。用户如果只接受手动导入，就要明确告诉他每次都得重导。

## 「多久会更新」

三家实测都**不是实时**，而且**都不能从客户端强制刷新**：

- Google 网页：两次实测 ≤3h31m、≤10h05m（官方只说"最长约 24 小时"）；10-13 试验田又给了
  第三个标点——抽掉 5 条不发墓碑后，4 条截至 T+14h39m 已移除、最后一条截至 T+24h58m 也已移除
  （删除的下界拿不到，仍然只是"小时级、不可预测"）。
- ColorOS：实测 ≤2h35m，能原地更新。
- Outlook.com：添加时立刻拉一次，此后实测 **14 小时以上未再回源**（官方口径约每 3 小时）。

用户催"怎么还没变"时，先报这个区间，再确认他改的那份**确实发布出去了**
（`doctor --verify` 的 URL 自检 + `subscribe status` 留底一致），别急着怀疑客户端。

**替用户做这类观测时一律用周视图**：Google 网页版的月视图单元格会**静默裁切**溢出条目
（连「另外 N 项」都不给），缓存还**滞后于服务端状态**。10-13 那次首读被月视图连骗了两回——
先误判"对照条目也被删了"，又误判"目标条目还在"，换周视图后一次读清。

## 「取消的考试怎么还在」

先分清"少掉一条事件"有**两种形态**，客户端反应不一样，别混着答：
**带墓碑**（`STATUS:CANCELLED` 仍在产物里 —— 真退课、改期、考试撤销走这条）与
**静默消失**（整段 VEVENT 没了、不发墓碑 —— 已过原定时刻、被过期筛放掉的条目走这条）。

四种结局，取决于客户端与形态：

1. **删干净** —— Google 网页版**两种形态都删**：带墓碑的实测会移除；
   不给墓碑、UID 直接缺席的**也删**（2026-10-13 试验田实测：96 → 91 事件、抽掉 5 条不发墓碑，
   **5 条最终全部消失**——4 条截至 T+14h39m、最后一条截至 T+24h58m，同批对照全在）⇒ 它的清理由
   **UID 缺席**驱动，墓碑不是触发条件。
2. **留一条「已取消的活动」** —— Outlook.com 与 ColorOS 实测**忽略**该字段，
   把撤销条目当普通事件导入。v0.6.1 起它带固定标题，所以一眼可辨；
   但它**不会自己消失**，要等原定时刻过去、条目从产物里退场。
   「退场后客户端会不会顺手清理」**已分家拿到答案（10-13）**：Google 会（缺席即删，见上面第 1 条）；
   ColorOS **不会**（见下面第 3 条）；Outlook 仍未取得。
   订阅型日历通常是只读的（Google 侧已确认没有"删除单条事件"的入口）。**别指望退订重加清得掉**：
   2026-10-12 整学期迁移演练实测，这条占位是**产物自身携带**的 `STATUS:CANCELLED` 事件，忽略该字段
   的客户端重加时会**再导入一遍**（重加后占位仍在、仍与新日程 1:1）。退订重加只能清本地重复项，
   清不掉占位——占位要等各自原定时刻过去后由下一次发布收掉。
3. **永久留着（幽灵条目）** —— 连墓碑都不给、直接从产物里消失的那一类，ColorOS **不会**清理：
   10-12 整学期演练里 21 条已过原定时刻的旧条目，在"删除日历 + 重新添加"之后仍在手机上。
   Outlook 这一格**未验证**（它从来没拿到过回源读数）。好消息是它们都落在**过去的时段**，
   日常视图里看不见，属于"脏但不挡路"；也正因如此，本工具**不打算**为过期条目补发墓碑
   （Google 侧本来就自愈，ColorOS 侧补了也不清，两头都换不到清理）。
4. **完全不动** —— 一次性导入型不回源。

## 「日历名不对」

名字来自产物的 `X-WR-CALNAME`，而客户端**通常在"添加"那一刻取一次**就不再更新：
Google 网页与 ColorOS 实测采用它，Outlook 忽略并强制手填。
产物后来改了名，**已添加的日历未必跟着变**——退订重加**通常**有效，
不重加会不会自己改名尚未验证。（2026-10-12 整学期迁移演练里，ColorOS 上"删除日历后重新添加"
**保留了旧事件**，说明该客户端的重加未必等于拿到一份全新数据，这条处置尚未在那台机器上复验。）
