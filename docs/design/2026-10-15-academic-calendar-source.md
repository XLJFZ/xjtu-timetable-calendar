# v0.9.0 校历事件 · P0 数据来源调查与设计决策

状态：**调查 + 设计备忘**（0.9-P0）。不实现功能、不动导出器、不碰订阅发布状态机、不提交任何真实校历数据。
范围裁定来自 2026-10-15 的两轮评审：UID v2 迁移已发布并核完字节，**订阅发布状态机就此冻结**；
v0.9 的第一笔只回答一件事——**校历事件的数据从哪来、能断言到什么程度**。

---

## 0. 一句话结论

**人工配置 + 官方一手页面做基线，eHall 接口在做完隔离探测并通过六条门槛之前不进正式数据源。**
现有 `Semester` 字段足以**算出**教学周日期，但**不足以断言**任何"学校发布的事实"（开学、考试周、寒暑假、
放假调休）——这两件事在本特性里必须分家，否则就是把推导冒充为学校公告（红线 3 的产品版）。

## 2. 现有模型能表达什么、不能推出什么

`models.Semester`（`models.py:71-106`）五个字段的全部能力就是：

| 字段 | 能可靠支撑 | **不许据此推断** |
| --- | --- | --- |
| `first_week_monday` | 第 N 教学周 ↔ 具体日期的换算锚点 | 新生报到日、开学仪式、实际上课首日 |
| `total_weeks` | 周次上限校验（越界 fail-closed） | 考试周是否独立于教学周、实践周、寒暑假起点 |
| `start_date` / `end_date` | 展示与范围校验（不参与逐事件计算） | 放假安排、调休、纪念日 |
| `key` / `name` | 配置索引与**事件 UID 的身份原料** | —— |

模型自己的注释已经写死了纪律：这两个字段**必须**是校历确认过的值，"没有官方依据时宁可留空"
（`models.py:85`、`:95-96`）。校历事件继承同一条：**没有来源就不生成事件**。

`AcademicCalendar`（`academic_calendar.py:34-101`）已经承载两类教学安排干预——`excluded_dates`
（全校停课日）与 `overrides`（`source_date` 调课 / `cancel` 停课 / `skip_meeting_keys` 单课跳过 /
`location` / `note`）。**注意语义差**：停课日表达的是"那天不上课"，它**不等于**"放假"这个对用户
有意义的日历事实——现在放假信息只在"抹掉课程事件"时间接现身，用户看不到"放假了"这条目。
这正是校历事件要补的洞，也是它不能靠 `excluded_dates` 反推的原因。

现成可复用的机制：`notices.py` 的公开 HTML → 结构化 → 合并配置整条通路（`_GridParser`、
`parse_teaching_notice`、`fetch_notice_html` 匿名 GET + scheme 允许清单、`apply_notice`、
`merge_into_config`），以及 `schedule_notice.py` 对官方作息页的处理。形态上更接近校历事件的是
**考试侧**（`exams.py:build_exam_events`：单场、绝对时刻、无 RRULE / 无 VALARM），不是课程侧的
RRULE 展开。

## 3. 三条路线的取舍与推荐

1. **A 人工配置为基线**（推荐，v0.9 第一版就走这条）：来源权威取决于用户抄的是哪份校历，
   但结构、校验、fail-closed 全在现有代码里，产物可预测，零网络。
2. **B 官方一手页面做校准 / 半自动录入**（推荐同期做）：`jwc` 通知是 HTML，`notice` 那条通路
   已经能匿名抓页面并合并配置；校历图片则只能"人抄一遍、把出处链接钉进配置"。
3. **C eHall 接口做增强**（**暂不接入**）：自动化潜力最大，但存在性、字段语义、跨学年可用性
   三件事都没证据。接入的唯一前提是 §9 那六条门槛全过。

**A+B 都不阻塞 v0.9 的排期**——这是本备忘最重要的结论：0.9 的进度不该被接口探测卡住。

## 4. 第一版事件模型草案（边界收得很紧）

只生成**有明确来源的全天事件**，五类之内可用，范围之外一律不做：

| 类别 | 语义 | 数据来源要求 |
| --- | --- | --- |
| `semester_start` | 学期开始 / 起课日 | 一手通知或校历（如 9/14 那条） |
| `registration` | 报到注册区间 | 一手通知 |
| `exam_period` | 期末考试周（学校公布的区间） | 校历；**不许**由 `total_weeks` 推 |
| `vacation` | 寒假 / 暑假区间 | 校历 |
| `holiday` | 学校公布的放假调休区间 | 一手放假通知 |

**第一批不做**：校庆与其他纪念日（第二批候选，且**绝不把纪念日理解成停课日**）、
"第 N 教学周起止"这类可由现有字段算出的区间（能算的不该做成事件，否则配置与推导会各说一遍）、
任何"上课提醒"类事件（提醒归客户端）。

每条事件的必填字段：`category`、`title`、`start`、`end`（闭区间，全天）、`source_url`、
`source_published_on`（可空）、`note`（可空）。落点建议：**进同一份学期配置文件的新 `events`
数组**，而不是再开一个文件——`AcademicCalendar.from_file` 的解析与校验路径已经在那儿，
`unsupported` 那道 fail-closed 门也在同一条路上，两处分开迟早漂移。

校验规则（全部 fail-closed，坏一条拒一条，不猜、不静默丢）：`category` 必须在枚举内；
`end >= start`；`source_url` 必须落在允许域名单内（复用 `notice` 已有的 scheme/域名允许清单）；
日期必须是完整 ISO 日期。**任何一条不满足 ⇒ 该事件不进产物 + warning（只报序号与字段名，
§8 口径照旧适用）**。

## 5. UID 与身份规则（现在定死，别等实现时随手写）

课程侧 v1 的教训是身份配方里掺了会改的字段（课程名），考试侧的教训是身份键必须优先用
服务端稳定行号（`WID`），两者都指向同一条：**校历事件要有一个显式的"来源事件 ID"。**

- **独立命名空间**，与课程 / 事件分开，配方：
  有 `source_id` 时 `semester_key | "cal" | source_id`；缺 `source_id` 时退化为
  `semester_key | "cal" | category | start | end`，并在日志记一条**降级**（与考试侧
  `WID → KSRWID → 内容组合` 同一形态，级别 INFO，不带 title 原文——§8 已经统一约束）。
- **学校改了日期算更新还是新事件？** 裁定：**配置里 `source_id` 不变 ⇒ 视为同一事件、原地更新
  （`SEQUENCE` +1）；没有 `source_id` ⇒ 改期即新事件。** 这条要在配置模板的注释里写明，
  让人工录入时主动给"寒假""期末考试周"这类年年都有的事实填稳定 ID（如 `2026-2027-1-winter`），
  把"漂移风险"交给配置而不是代码默认。
- **不接撤销通路**：0.9.0 第一版的校历事件**不参与**课程侧 / 考试侧那套撤销与熔断逻辑
  （发布状态机已冻结）。代价要如实写：旧事件从 feed 消失后，会回源的客户端会删（Google 已实测），
  "消失永不删"的客户端（ColorOS）会残留——这与迁移那笔是同一类代价，不新增机制去掩盖它。

## 6. 两个必须先定的技术前置（实现前复核）

1. **全天事件与 `SEQUENCE` 基线**。`tests/test_exams.py:289-296` 那条用例记录着一个既有事实：
   `parse_baseline` **静默丢弃非 DATE-TIME 事件**，"进不了基线的事件，客户端永远不会收到更新"。
   校历事件天生是 `DATE` 全天 ⇒ 照现状实现会得到一个"每次重发布 SEQUENCE 恒 0、改了也不更新"的
   哑事件。所以实现前必须先决定：要么让基线认 `VALUE=DATE`（并补一条先红用例），
   要么第一天就用 00:00–23:59 的 DATE-TIME（语义上诚实度低一档）。**本备忘倾向前者**，
   并把这条列为 0.9-P1 的第一个施工项。⚠️ 这条判断的依据是那条用例的说明，
   **本轮没有重新读 `sequence.py` 的实现**（P0 范围），实施前必须实测复核。
2. **默认关还是默认开**。裁定：**默认关，`--include-calendar-events` 显式打开**（并与
   `--no-exams` 一样贯通到 `subscribe push` / `rotate`）。理由与考试侧当年默认并入不同：
   考试数据是本人课表的自然延伸、来源是认证接口；校历事件在 v0.9 第一版来自人工配置，
   来源缺失/抄错的可能性高，而它会进**所有订阅者**的日历。默认关还顺带守住一条既有不变量——
   **现有订阅者的产物字节不因启用新特性而变**。

## 7. 冲突处理与可见性

- 两个一手来源互相矛盾（例：校历图片与通知文本给出不同日期）⇒ **两边都不生成事件**，
  在配置里记一条 `conflict` 说明，`doctor` 出**警告**（不阻塞），并把两条链接一起打出来给人看。
  本特性不许自动择一——择一就是把猜测写进公开产物。
- `doctor` 增一格「校历事件：N 条（来源 M 个）」，并单独打「有 K 条被拒绝 / J 组冲突」；
  口径沿用"体检不能比门更凶"：事件被拒不改退出码，除非出现"配置声称有事件但一条都没解析出来"
  这种自相矛盾（那时才算阻塞项）。
- 日志一律遵守 §8 那条统一约束：行号 / 序号、字段名、计数、异常类名、UID 可以出现；
  事件标题与来源 URL 的**值**不进日志。

## 8. eHall 探测的前置条件（含一条必须避开的现有坑）

**现有 `scripts/probe_ehall.py` 不是零副作用探测器**，本轮逐行核过：
`settings.ensure_dirs()`（`:332`）、建探测目录（`:333-336`）、用**真实浏览器 profile**
启动持久化上下文（`:365`、`:372`）、**结束时覆写 `storage_state.json`**（`:415`）、
把含原始 payload 的捕获写进 `~/.xjtu-timetable-calendar/probe/`（`:439`）。
脚本自己的说明里也矛盾：`:18` 把"不保存 storage_state"列为旧版缺陷，`:26` 承认现版会保存。
⇒ **不得在真实 home 上跑它并把结果称作只读取证**（评审判断成立，本备忘据此设门）。

探测的正确姿势（P0 只写方案，不执行）：

1. **先做完公开来源调查**（就是本备忘这一份 + §9 的字段清单），带着"要找什么字段"去探，
   而不是先探再猜。
2. **隔离探测器**：`_notes/` 下一次性临时 home + 一次性浏览器 profile，
   通过 `XJTU_CALENDAR_HOME` 指进去；跑完即删；**不改跟踪代码**、不覆盖现有会话/raw/subscribe
   /发布凭据。判据：跑完真实 home 的 mtime 与 sha 一字不变。
3. **用户前台完成认证**：本人正常登录、进到实际可见的校历/教学日历功能，**只观察前端自己发出的
   请求**。不猜接口地址、不枚举路径、不高并发（这条与 `ehall_endpoints.json` 的
   `_readme` 是同一条纪律：路径的唯一合法来源是真实观测）。
4. **只输出脱敏结构证据**：请求路径、方法、参数**键名**、响应状态、JSON 层级与数据类型。
   原始响应、Cookie、token、任何个人字段都不进可分享报告——探测报告的模板要求先过一遍
   隐私 grep 才允许离开 `_notes/`。
5. **交叉核验**：探到的日期与事件类别一律回到 `due` / `jwc` 一手页面比对；
   出现矛盾保留冲突记录，不自动择一（同 §7）。
6. 探测期间**不执行** `fetch`、`subscribe push`、`subscribe rotate`。

## 9. 接入 eHall 接口的六条门槛（全过才谈正式数据源）

| 门槛 | 判据怎么量 |
| --- | --- |
| 接口真实性 | 该路径只出现在正常页面操作触发的请求里，且能在探测报告中指到具体一次观测 |
| 权限 | 当前用户正常权限即可访问；401/403 的重放路径不靠任何凭据外泄 |
| 数据结构 | 能区分事件类别与起止日期（不是整页 HTML 里的人话） |
| 语义正确性 | 至少 3 个已知官方日期逐条对上（开学、考试周、寒假起点是天然的三个探针） |
| 稳定性 | 同一会话内重载结构一致；**跨学年可用性单独验证**（换 `XNXQDM` 拿得到上一学年的数据才算通过） |
| 异常处理 | 401/403、空数据、字段缺失三种情况下**一条事件都不生成**，且退出码与日志口径符合既有降级规则 |

任何一条不满足 ⇒ 保持人工配置路线，**不阻塞 0.9.0**。

## 10. Non-goals 与下一步

- 不改订阅发布状态机（冻结）、不动 UID v1→v2 之后的任何撤销语义、不新增撤销类别。
- 不做服务端定期重新生成、不发墓碑（这两条早在 followups 里裁定过）。
- 不把校历图片 OCR 成数据源（本轮连下载都没做；OCR 的错字率会直接进公开产物）。
- 不提交任何真实校历数据进仓库（跟踪内容里的校历一律用合成日期，红线：仓库不含真实数据）。

**下一步（要用户点头才开）**：0.9-P1 拆两笔——
①「全天事件进 SEQUENCE 基线」的先红用例与修复（§6.1，实施前必须实测复核）；
②`events` 数组 + 事件构建 + `--include-calendar-events` 贯通 CLI/订阅/文档。
§8 的隔离探测器只在①②之后、且用户愿意配合一次前台观测时再排。
