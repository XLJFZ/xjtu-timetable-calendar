# 按症状排查

每条给出**判据**（怎么确定是这个症状）与**处置**（做什么）。判据一律来自命令输出、
文件修改时间或 `doctor` 的检查项，不来自"看起来没报错"。

## 装好了却跑不动：`login` 报「登录功能需要 playwright」／`fetch` 报「HTTP 路径需要 httpx」

- 判据：`xjtu-calendar --version` 正常，但 `login` 一上来就 `[错误] 登录功能需要 playwright`；
  或 `fetch` 报 `HTTP 路径需要 httpx`。
- 原因：**基础包只依赖 `icalendar`**，`playwright` 与 `httpx` 分别装在 `[browser]` 与
  `[http]` 两个 extras 里。裸 `pip install xjtu-timetable-calendar` 得到的环境
  能解析、能导出，但走不到第 2 步以后（2026-10-14 干净虚拟环境实测）。
- 处置：`pip install -U "xjtu-timetable-calendar[http,browser]"`（**带引号**，
  `[]` 在部分 shell 里会被解释）；源码安装用 `pip install -e ".[http,browser]"`。
- 判据回收：`python -c "import httpx, playwright"` 两句都不报错。

## `fetch` 返回 401 / 跳回登录页

- 判据：`fetch` 报会话失效或产物压根没更新；`doctor` 的「会话」一项为警告或阻塞。
- 处置：`python -m xjtu_calendar login --force`，**在用户自己的前台终端里**。
  注意 `login` 不带 `--force` 时不会重登（见下一条），过期会话必须用 `--force`。
- 判据回收：会话文件的**修改时间变化**，然后 `fetch` 不再 401。只看命令有没有非零退出
  不够——它可能压根没弹浏览器。

## `login` 看起来成功，其实什么都没做

- 判据：终端打印了「已检测到本地会话」之类的话就退出了，但会话文件的修改时间
  **纹丝不动**。
- 原因：工具看到本地存在会话文件就直接短路返回，**不验证它是否还能用**。
  那句提示的意思是「沿用本地会话（未验证有效性）」。
- 处置：改用 `login --force`。任何时候用户说"我登录过了"而 `fetch` 还 401，先查
  mtime 再争论。

## `fetch` 报 403（不是 401），提示「没有访问该接口的权限」

- 判据：`fetch` 的退出码是 **4**、错误行是「接口返回 403：timetable」；`doctor` 的
  「会话」一项警告「会话里没有教务侧（/jwapp）的 cookie」。会话文件里
  `path` 以 `/jwapp` 开头的 cookie 条数为 **0**（正常登录是 4 条：
  `JSESSIONID`、`_WEU`、`THEME`、`EMAP_LANG`）。
  **还有第二种形态**：条数不是 0、却缺那条承重的 `_WEU`（`doctor` 会说
  「有 M 个 cookie，却没有承重的 `_WEU` 票据」）——别因为它不是 0 就判定会话是好的。
- 原因：**登录只走了一半**。`login` 打开的是「请选择身份」页面，在那个页面上就按
  Enter 的话，抓下来的会话过得了统一身份认证、却没拿到教务应用发的 cookie，
  于是课表 / 学期发现 / 考试三个接口一律 403（返回的是学校平台的异常页 HTML，
  不是登录页，所以 401 分支抓不到它）。**不是账号被收了权限。**
  2026-10-14 实测补一条：真人**点了**「学生」也照样可能中招——点完到课表渲染出来中间
  有几秒跳转，那期间按 Enter 会存下 33 条纯门户 cookie、教务侧 0 条；同一份会话
  headless 重放再点一次「学生」，立刻落到 `/jwapp/sys/wdkb/...#/xskcb`、四条齐。
  差的只是等待，所以 `login` 现在自己轮询教务侧 cookie（最多 20 秒 + 追问后 6 秒），
  没等到不关窗口。**今天仍报 403 的话，说明用户在追问那一轮选了放弃或超时。**
- 处置：重跑 `login --force`，在窗口里点「学生」并**等到课表真的显示出来**再按 Enter。
- 已排除的猜测（2026-10-14 消融实测，别再往这些方向折腾）：换浏览器
  `User-Agent`、补 `Referer`/`Origin` 都不改变 403 ⇒ 不是站点在拦非浏览器客户端；
  两份同名 `JSESSIONID` 少任意一份仍然 200 ⇒ 承重的不是"哪份 JSESSIONID 被留下"，
  而是 `_WEU` 在不在。
- 判据回收：`doctor` 的「会话」一项转为通过，`fetch` 退出码 0。

## 把 `login` 放进了后台执行器或管道，于是卡住

- 判据：任务输出 0 行；会话文件 mtime 没变；一个浏览器窗口挂着并占住了工具的会话目录。
  执行器可能报告"运行中"——那个状态没有意义。
- 原因：`login` 源码里有 `input()`（登录完成后终端要等一句 Enter）。放进
  `... | tail -20` 或后台执行器里，它永远等不到回车。
- 处置：终止那个后台任务，关掉残留的浏览器窗口（是工具自己弹出的那个实例，
  不是用户日常用的浏览器），然后把命令**原样**交给用户，让他在前台终端里跑。
  这类步骤没有变通写法，别再试第二次。

## 弹出的浏览器是一片灰页（**别拿 `?browser=no` 当判据**）

- 判据：窗口能打开但**没有任何可见内容**。
- **`?browser=no` 不是症状**：它是 eHall 服务端在 CAS 回跳的最后一步给落地页拼上的固定参数
  （`/login?service` → 302 → `/new/index.html?browser=no`），本工具代码里从不拼这个参数。
  2026-10-08 一份**成功登录**的接口捕获里它同样存在，且其后一路 200 打到
  `studentWdksapApp` 的课表与考试接口。所以：带它 ≠ 坏了，不带它 ≠ 好了。
  以前把这条当判据是错的——它会把好会话误判成故障，也会让真灰页因为不带它而被漏认。
- 处置：先在该窗口的地址栏**手动输入**终端里打印的入口 URL；仍不行时让用户换浏览器——
  用环境变量指到另一个可执行文件：

  ```cmd
  set XJTU_CALENDAR_BROWSER=C:\path\to\browser.exe
  python -m xjtu_calendar login --force
  ```

  （cmd 里 `set` 单独一行；`VAR=value 命令` 那种 bash 写法会被当成命令而报错。）
- **成因仍未证实**，别向用户承诺已定位。现有线索：10-07 那四个失败样本都跑在**后台任务
  执行器**里（其中一次的 `lost sys.stdin` 证明该执行器会弄坏子进程 stdio），而 10-08 用
  **同样的启动参数 + 真实 profile** 在前台跑独立探针时渲染正常（3012 可见字符 / 668 个 DOM
  节点 / `navigator.webdriver: False`）⇒ 最大嫌疑是执行器而不是 eHall 或本工具。
  要坐实需要一次真机 `login`（交互式，只能用户本人跑），观察点是窗口里的
  `document.body.innerText.length` 与最终 URL，而不是地址栏有没有 `browser=no`。

## 警告「eHall 域范围内出现同名 cookie：JSESSIONID」

- 判据：每次 `fetch` 都出现这一条 warning。
- 处置：**不用管**。2026-10-11 用刚重登的干净会话实测，这条警告依旧出现，课表与学期
  发现接口都正常返回。它是同一域下多份同名 cookie 的取舍提示（程序取最后一份）。
- 例外：只在它**伴随 401** 时才说明会话真的坏了，那时按本节第一条重登。单独出现时
  不要去"修"它。

## 日历里没有考试

按顺序查三件事，别跳步：

1. **走的是哪条抓取路径。** 只有默认的 HTTP 路径会抓考试。`fetch --from-file`（离线导入，
   没有会话）与 `fetch --source browser`（按课表关键词过滤捕获的 URL，考试接口路径不在
   关键词里）**明确不抓考试**，日志会说明原因。处置：用默认路径 `fetch`。
2. **考试快照是三态里的哪一态。** 接口"没有考试"和"查询失败"返回的行数**都是空**，
   判定落在响应的 `extParams.code` 上，分「有考试 / 确认无考试 / 状态未知」。
   状态未知时工具**不覆盖旧快照**，warning 会报出沿用的是哪一天的数据，或明说本地没有
   考试快照。看 `doctor` 的「考试快照」一项与 `fetch` 的 warning 原文。
   处置：UNKNOWN **不等于"本学期无考试"**，不要为此改配置或宣布没有考试；重新登录再
   `fetch` 一次。
3. **渲染口径有没有把考试关掉。** `--no-exams` 只有**四条路径**认它：`fetch`（侧是**不抓**）
   与 `export` / `subscribe push` / `subscribe rotate`（侧是**不并入**）。
   **`subscribe init` 没有这个旗标**，别往它后面加。两种情况本地快照
   `raw/exams-<学期>.json` 都不删除；但发布侧要如实告知「`--no-exams` 既不发布考试、
   也不发布撤销」——撤销的下发顺延到开关重新打开之后。看 `doctor` 的「渲染」一项报的
   考试场数。处置：去掉 `--no-exams` 重新导出/发布。

## 撤销的考试残条不消失

- 判据：客户端里那条标题为「已取消的活动」的日程还在。
- 先分辨客户端（见 `client-matrix.md`）：Google 网页版实测会删掉带 `STATUS:CANCELLED`
  的日程；Outlook.com 与 ColorOS **忽略**该字段，把它当普通事件留下。
- 处置**分通路，别一句概括**：**ICSx⁵ 上用户自己删得掉、且同步后不会再加回来**
  （2026-10-19 实测，界面级判据）——这是最省事的出路，可以直接告诉用户；
  **ColorOS 系统日历三条路全部无效**（手删 / 退订重加 / 删除订阅，2026-10-15 实测），
  原定时刻过去、条目从产物退场之后它**也不清**，这条通路上等不到自动清理。
  "条目从产物里消失之后客户端会不会清掉"同样分通路：ICSx⁵ 每次成功同步末尾无条件 prune
  （2026-10-19 实测会清），ColorOS **永不删**（10-12 整学期演练：过期旧项重加后仍在）。
  **别拿退订重加当"立刻清干净"**：2026-10-12 迁移演练实测，这条占位是产物自身携带的
  `STATUS:CANCELLED` 事件，忽略该字段的客户端重加时会**再导入一遍**（重加后仍在、仍与新日程 1:1），
  退订重加只能清本地重复项。
- 一次性导入型客户端完全不回源，收不到撤销，只能手动删；固定标题就是给手动删用的
  辨认线索。

## 日历名不对 / 改了名没更新

- 判据：客户端显示的日历名与产物里的 `X-WR-CALNAME` 不一致。
- 原因：客户端**通常在"添加"那一刻取一次名**就不再更新。Google 网页与 ColorOS 实测
  会在添加时采用；Outlook.com 完全忽略、强制手填。
- 处置：退订再重新添加**通常**有效（2026-10-12 演练在 ColorOS 上观察到"删除后重加仍保留旧事件"，
  所以这条不是保证，改完要让用户确认日历确实变干净了）；不重加会不会自己改名尚未验证。用户不接受重加时，
  教他改客户端的显示名（Outlook 只能这么办）。

## `subscribe push` 报退出码 `8`（校历事件，0.9 起）

- 判据：报错原文第一行是「校历事件的发布准入未通过，本次不发布（远端与本地状态一字未动）」，
  退出码 `8`。三种触发：①带了 `--include-calendar-events` 而学期配置 `events` 有错；
  ②带了它而 `conflicts` 里有**未裁决**的冲突（`adjudicated_by` 为空）；③上一次发布的产物里
  有校历事件，这次**没带**那个旗标。
- 处置只有**改配置**这一条。`subscribe repair` 管的是本地状态与线上不相容（退出码 `7`），
  `--allow-mass-cancellation` / `--allow-unverified-baseline` 管的是另外两道门——
  对 `8` 全都不相干，拿它们去试等于绕开用户真正该修的那一行 JSON。
- 报错文案里只有**配置序号、字段名、原因码与计数**（设计文档 §8 的零原文口径），
  不会有事件标题。把它读回给用户时也别替它补上标题——那等于把公开产物里的原文搬进对话。
- 预防：配置改完先跑 `xjtu-calendar doctor --semester <标识> --include-calendar-events`
  （体检与门共用判据；不带那个旗标就是"按普通发布判"）。

## 日历里没有校历事件

- 先确认版本：`--include-calendar-events` 与退出码 `8` **自 0.9.0 才有**。停在 0.8.x 的用户
  会拿到 `unrecognized arguments`，那不是配置错，是他的版本没有这个功能——先 `pip install -U`。
- 再确认旗标：这个特性**默认关**，`export` / `subscribe push` / `subscribe rotate` 三处都要
  显式带上旗标；`subscribe init` 没有它（init 不构建产物）。
- 再看 `doctor` 的「校历事件」那一格：它报"几条可用 / 几条配置错误 / 几组冲突未裁决"。
  被未裁决冲突点名的条目**两边都不生成**（§7：择一就是把猜测写进公开产物）。
- ⚠️ 告诉用户这笔代价：校历事件**不接撤销通路**。把 `events` 条目删掉 = 事件从 feed 消失，
  不下发 `STATUS:CANCELLED`；**之后再加回来会按新增事件重发，`SEQUENCE` 从 `0` 重算**，
  而客户端此前见过的是更高的序号——它**通常**不会用更低的序号覆盖本地那条（真机未针对
  校历事件验证）。`subscribe repair` 只对齐本地留底与台账，**修不了客户端已持有的历史状态**。
  所以"删了再想加回来"不是无损操作，删之前要跟用户确认。

## 改了校历里的 `key`，客户端里整学期"多出一份"

- 判据：用户说"我没改课表，只是把配置里的 key 改成和文件名一致，日历就重复了"；
  `subscribe push` 的日志里出现成批的「无法安全下发撤销（发布留底里没有这个 UID）」。
- 原因：`semester.key` **会进入每一条事件的 UID**。只改这一个字段（文件名、日期都不动）
  再导出，UID 会**整批换掉**（2026-10-14 实测：103 个 UID 零交集），订阅端于是把旧的
  一整批留下、再导入新的一整批。
- 处置：`doctor` 的「学期校历」一项会在 `key` ≠ 文件名标识时**警告**——看到它就先停下，
  别顺手改。已经改过并推送过的，只能按"客户端会留旧事件"处理（退订重加清不掉产物携带的
  墓碑，见 `client-matrix.md`）；未推送的，把 `key` 改回原值即可，UID 会复原。
- 预防：README 的格式示例里 `key` 与示例文件名是一致的（都是 `2026-fall`），
  换自己的标识时**两处一起改**。

## 「导入」还是「订阅」？

- 判据：看客户端的入口名与有没有**「上次同步时间」**。带同步时间的是订阅型，会定期
  回源；一次性导入型只有显示开关，没有任何同步记录。
- 这一步必须在用户完成添加后**当场确认**，不能凭"他是从 URL 添加的"来推断。
- 为什么关键：一次性导入是快照，之后 `subscribe push` 多少次都收不到变更与撤销。
  分辨错了，后面所有"怎么没更新"的排查都是白费。

## 怎么确认整个部署到位

```bash
python -m xjtu_calendar doctor --verify --semester <学期标识>
```

退出码 0（`结论：0 项阻塞 / N 项检查`）才算到位；5 表示有阻塞项，按打印出的标签回到
对应步骤。警告不阻塞，但要逐条向用户解释它意味着什么。

## `doctor` 的「订阅」一项判阻塞（退出码 5）

- 判据：这一项的文案里有「本地发布状态与已发布版本不相容」，并点名 `subscribe repair`。
- 含义：`subscribe push` 对**同一个状态**会返回 `7`。两者跑的是同一条判定
  （`check_local_compatibility`），所以别去折腾登录、校历或重新 fetch——那些与此无关。
- 处置：`python -m xjtu_calendar subscribe repair --semester <标识>`。它先从发布分支拉回
  线上真实字节，再在两份恢复凭据之间裁决，**不产生新发布**；跑完再 `doctor` 就该回到 0。
  可重复执行，中途再断一次，第二次接着补剩下的。
- 同一道门也装在 `subscribe rotate` 上（换 token 的补发与 push 共用一条发布事务），
  而且排在**换 token 之前**：被 `7` 拦住时旧 URL 依旧好用，先 `repair` 再 rotate。
  rotate 若在推送**之后**才失败（提示改指 `subscribe repair`、返回 `7`），那是"远端可能
  已经挂上新文件名"的窗口——按提示 `repair` 裁决，别直接重跑：两份凭据里那份待裁决的
  准备稿是唯一的线索。
- 两种**不该**判阻塞、只判警告的格子（别多跑一次 repair）：
  ① 从 0.8.5 之前升级上来、本地还没有恢复凭据，而留底字节与「最后一次发布记录」逐字节相符
  ⇒ 警告会说"两份台账与迁移标记这次没能校验"，直接 `push` 会自行把依据补回；
  ② 有未发布变更（课表确实变了）⇒ 正常 `push` 即可。
- 真修不动的那一格：`repair` 会说「仍有本地状态无法恢复」——那是 `--no-exams` 类发布只给
  被保留的台账留了指纹、没留内容，需要从备份找回原文件，或在确认可以接受丢掉这段撤销
  历史时带 `--allow-unverified-baseline`。

## `doctor` 报「未指定学期」就退出

- 判据：只有一行 `[错误] 未指定学期`，没有任何检查项；退出码 **1**（不是 5）。
- 处置：加 `--semester <标识>`，或设置环境变量 `XJTU_SEMESTER`。这是"没告诉它查哪个
  学期"，不是"体检没过"——别把它当成阻塞项去回头折腾登录。
