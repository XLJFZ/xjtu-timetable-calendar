## 0. 一条先行的判断：别再优化产物格式

演练过程中把产物的结构兼容性实测了一遍：`VTIMEZONE` 块、`X-WR-TIMEZONE`、统一 CRLF、
长行折叠**都在**，三家客户端（Google / Outlook / ColorOS）都能正确解析时间与中文。
两个已知小瑕疵都不值得动：

- 最长行 76 字节（RFC 5545 建议 ≤75，实测三家全接受，且由第三方库折叠，改它等于跟库较劲）；
- 内嵌的 Asia/Shanghai 时区定义带「只适用于 1970–2038」的注释（我们的事件永远在一学期内）。

**泛用性的瓶颈全部在客户端语义层**，不在编码层。下面几条都是语义/分发/操作层的议题。

## 1. 撤销条目的固定标题（v0.6.1 候选，成本最低）—— **已落地（2026-10-11）**

**落地形态**：`exams.CANCELLATION_SUMMARY = "已取消的活动"`，由 `build_cancellation_events`
赋给每条撤销事件；`render_ics` 那个"空标题不写行"的条件保留，职责退化为纯空值守卫。
规格侧 D3 已就地修订（`2026-10-09-exam-cancellation.md` §2 的 D3 行、§6.2 注、§9 新增用例），
三条新用例钉住：标题恒为该文案、产物不含台账原文、多条撤销标题两两相同（SEQUENCE 不漂移）。
下面原文保留，作为当时的判据记录。

**现状证据**：撤销条目按 D3 刻意不含 `SUMMARY`。认 `STATUS:CANCELLED` 的客户端（Google）
会直接移除，无影响；**不认的客户端（Outlook.com、ColorOS，均实测）把它当普通事件导入**，
于是留下一条**没有标题**的日程——用户既认不出它是废弃条目，也不知道该不该删。

**改动面**：`exporter.py` 的撤销分支给一个**不含任何个人信息**的固定标题（例如
「已取消的活动」）。隐私代价为零：不新增姓名/考场/座位/课程名。
D8 的序号幂等不破：标题每次渲染都相同 ⇒ `event_fingerprint` 输入不变 ⇒ 序号不漂移。

**前置条件 —— 已满足（2026-10-11 15:3x 真机读数）**：ColorOS 对已存在事件做的是
**整体替换字段**，不是逐字段合并：演练最后一步把已经带标题显示过的丁转成撤销条目
（同一 UID、`SEQUENCE` 递增、新版本不含 `SUMMARY`）后，手机上那条日程**变成了「无主题」
但没有消失**（旧标题被清掉了）。⇒ 加了固定标题之后，**手机上的取消过程会自动变成一条
写着「已取消的活动」的日程**，用户零操作。这一项因此从"待验证"升级为"可直接排期"。
（Outlook.com 侧的同一转换尚未观测到——它 14 小时以上没有回源，不能替它下结论。）

**要同步改的**：`docs/design/2026-10-09-exam-cancellation.md` §9 里钉着一条用例
「产物中不得出现 `SUMMARY:` 空值行」——那是 D3 的看守。本改动会把它从"不许有标题行"
改成"标题行只能是那个固定值"，属于**规格变更**，不是让测试变绿的手段。

## 2. 课程撤销通路（**v0.8 候选**，价值最大、风险也最大）

> 版本号注（2026-10-11）：本项原占 0.7.0，因 `doctor` 是新增 CLI 能力而让位到 0.8.0，
> 见 `docs/design/2026-10-11-agent-skills.md` §3.1 的拍板记录。

> **落地形态（v0.8.0，2026-10-12，见 `2026-10-12-course-cancellation-uid-v2.md`）**：本节已实现，
> 但**比这里的原计划多做了一步根治**——原 §2「不做的事」写「不改 UID 配方」，被 CD1 推翻：
> 单纯把考试那套搬到课程上会让改名表现为整学期几百条「已取消的活动」，所以 v0.8 同时把课程 UID
> 换成配方 v2（去掉 `course_name`，改名走原地更新，`course_id` 缺失时仍退回 `name:课程名`，CD16），
> 并在 `subscribe push` 上做一次性 v1→v2 迁移（`export` 不参与，CD3）。上面三条前置条件全部落地：
> 门 1 数据可信（`assess_courses`，CD13）+ 门 2 比例熔断（≥ 10 条且 ≥ 台账 30% 即拒绝发布、
> 退出码 `6`、`--allow-mass-cancellation` 放行，CD12）、课程台账
> `subscribe/last-courses-<学期>.ics`（CD8）、`--from-date/--to-date` 裁剪零影响（过滤前捕获 live 集，CD14）。
> **本项没有搭车的部分**：`.webcal` 分发（下面 §3）明确不在本版——CD19 把它排到 0.8.x 独立一笔。
> 下面原文保留，作为当时的判据记录。

**现状证据**：课程 UID 的配方**包含课程名**（`exporter.py:95` 起写明是 legacy 契约：
自 v0.1.0 就随正式版发布，改它会让已导入用户的整学期被识别成新事件，需要显式迁移方案）。
于是**改课名 / 换任课老师导致课程行身份变化**时，订阅端的表现是「旧事件消失 + 新事件出现」，
而 v0.6 的撤销通路按 D17 **只管考试、不管课程**——旧的那批事件**永远不会被收掉**，
残留的还是带真实课程名的整学期日程。

这个场景在学期中比「考试取消」常见得多，后果也更糟，是目前最大的一个泛用性/正确性洞。

**为什么不能照搬考试那套**：撤销候选 = 台账 UID − 本次 live UID。对课程而言，
"本次没有课程"和"课表没抓到/解析炸了"在现有代码里**返回的都是空集**——正是 spec D18
给考试侧补的那道门槛要防的失败模式，而且课程侧的后果是**撤销整学期课**。

**前置条件（缺一不可）**：

1. 课程侧的可信度门槛，强度不低于 `exams_trusted`：快照来源可信、行数不低于一个下限、
   单次撤销数量占既有事件的比例超过阈值就**拒绝发布**并报错；
2. 课程台账（与 `last-exams-*.ics` 同等待遇：本地私有、全字段、发布成功后才回写）；
3. 明确 `--no-exams` 那类"渲染口径开关"在课程侧的对应物（`--from-date`/`--to-date`
   裁剪会不会被误判成"课程消失了"——D19 的教训在这里更尖锐，因为裁剪是常态操作）。

**不做的事**：不改 UID 配方。UID v2 需要迁移方案，是另一份规格，不该被这个议题顺带夹走。

## 3. `.webcal` 分发 → **改为输出 `webcal://` 链接，不发 `.webcal` 文件**（0.8.x 决定，2026-10-12）—— **已落地（2026-10-12）**

**决定与理由**（原方案是"在 `.ics` 旁边多写一个 `<token>.webcal`"，四条理由否决）：

1. `webcal://` 本来就是 **URL scheme**，不是文件格式——`.webcal` 文件的内容就是一行 webcal URL。
   我们的 `.ics` 已经有稳定 URL，把 scheme 换掉就是同一个地址 ⇒ **不需要任何新文件**。
2. 发布分支的 tree 护栏断言「根目录恰好一个 `*.ics`」（`subscribe.py:279-291`）。多一个
   `<token>.webcal` 会让 `len(listing) == 2` ⇒ **下一次发布被自家护栏判成"分支被污染"而拒绝**；
   要放行就得放宽护栏，而护栏的职责正是"别把用户的工作仓库强推覆盖掉"，为省一个链接去削它不值。
3. `rotate` 会换 token，而清理只 `unlink` `*.ics`（`subscribe.py:297`）⇒ 旧 `<token>.webcal`
   会留在 tip 上，同样撞死护栏。这是原方案里没写到的新 bug 面。
4. 多一个公开文件就多一个可枚举面（本文第 4 条），而且 GitHub Pages **不能设自定义
   `Content-Type`**，`.webcal` 多半以 `application/octet-stream` 下发，在 iOS 上反而不如
   直接点 `webcal://` 链接可靠。

**落地形态（2026-10-12，0.8.x 的第一笔）**：`SubscriptionState` 有了只读属性 `webcal_url`
（`subscription_url` 的 `https://` → `webcal://` scheme 替换；非 https 的 `url_base` ——
明文 `http`、`file://` 彩排远端 —— 返回 `None`），CLI 的 `_print_webcal_hint` 在**四处**各打一行：
`subscribe init`、`subscribe push`（含 `NO_CHANGE` 那一支——幂等跳过往往是用户第二次看到入口）、
`subscribe rotate`（打的是**新** token 的链接，旧链接随之作废）、`subscribe status`。
文案为「iOS/macOS：通常可直接打开 <链接> 完成订阅（真机未验证，失败就走 README 的手动路径）」。
发布分支的 tip 形态**未变**，仍然只有一个 `<token>.ics`（有用例钉住）；README 补了
「iOS / macOS：`webcal://` 订阅链接」一节给出手动路径与三条口径，`skills/` 的第 7 步与
`references/client-matrix.md` 同步，并写明这一改动不产生新发布物，防止下一个 agent 又去发文件。

**红线 3 仍然适用**：「iOS/Safari 点 `webcal://` 会弹订阅确认」是常识但**未在本项目真机验证**，
输出与文档一律写「通常」并注明未验证。iPhone 侧的端到端订阅（点了到底弹不弹、订阅后是否定期回源）
仍是**待做的真机演练**，本轮只落了链接与文案。

### 原方案存档（为什么曾考虑发文件）

**现状**：iOS/macOS 的订阅入口藏在「设置 → 日历 → 账户 → 添加账户 → 其他 →
添加已订阅的日历」，用户要手贴 URL；而 `.webcal` 链接点一下就能完成订阅。

**改动面**：发布时在 `.ics` 旁边多写一个 `<token>.webcal`，内容只有一行
`webcal://…/<token>.ics`。GitHub Pages 托管任意静态文件，不需要额外配置。

**代价与风险**：① 发布分支的 tree 护栏现在断言「根目录恰好一个 `.ics`」，
新增扩展名要确认护栏计数口径不被误伤（它按 `.ics` 后缀过滤，理论上是安全的，但必须实测）；
② 多一个公开文件就多一个可枚举面，见第 4 条；③ README 要加一句 iOS 路径。

## 4. 订阅 token 的公开面（口径问题，不是功能问题）—— **措辞已落地（2026-10-11）**

**落地形态**：README 的两处口径（「URL 订阅 → 隐私口径」与「隐私与安全 → 订阅 URL 的
风险口径」）与站点落地页的隐私节，全部改成诚实版本——暴露面有**两处**：转发 URL 等于授权，
而公开仓库的分支文件列表页匿名可读、会直接列出 `<token>.ics` 的文件名；同时写明
「产物里有什么就是公开什么」（默认并进的考试事件会把考试名、时间、考场与 `DESCRIPTION`
里的座位号放进那份公开产物，`--no-exams` 可关）。仓库根 `skills/` 的第 7 步本来就已经
如实告知这一层，现在三处口径一致。
**没有落地的部分**：本节列出的三个方向**一个都没选**——发布仓库转私有受免费账户限制（见第 7 条）、
换托管暂缓、"接受现状"现在成了默认口径。措辞只是不再高估保护强度，**不等于暴露面被修掉了**。
下面原文保留，作为当时的判据记录。

**现状证据**：发布仓库是**公开**的，`tree/<分支>` 页面匿名可读，会**直接列出**
`<token>.ics` 的文件名。也就是说 README「风险口径」里那句「URL 里的随机 token 猜不到，
但知道 URL 就能读」——它的**第一层保护在公开仓库上并不成立**：不需要猜，浏览分支就能拿到。
token 仍然挡得住"别人不知道有这个仓库/分支"这一层，但挡不住任何会看分支列表的人。

**这不是演练的一部分，也不该由文档悄悄改掉**。可选方向（各自都有代价，需要用户拍）：
发布仓库转私有（GitHub Pages 对私有仓库要付费档）、换非公开分发（网盘 / 本地文件 +
ICSx⁵ 那条零公网暴露的链路）、或者接受现状但把 README 的措辞改成诚实版本
（「任何能浏览该仓库分支的人都能拿到课表」）。

## 5. 客户端行为矩阵的维护方式（流程，不是功能）

README 现在有一张矩阵表（Google 网页 / Google App / Outlook.com / ColorOS / 一次性导入 ×
订阅入口 / 认不认取消 / 自动回源 / 用不用 `X-WR-CALNAME`）。它的问题是一次性：
客户端会改版，厂商口径和实际行为也会分叉（本次就实测到 Outlook 官方"约每 3 小时"
对上 14 小时以上未回源）。

**建议的纪律**：① 表里每一格都要有「实测日期 + 设备/版本」的限定，不写无条件事实；
② 每次发布前如果动了撤销或 UID 语义，至少重跑 Google 那一行；③ 新客户端（MIUI / 鸿蒙 /
iOS 原生）按同一列结构补行，**没验的格子写"未验"而不是留空或照抄别家**。

**本次演练里矩阵欠的两格**（顺手可得，下次动到相关面时补上）：

- **产物改名后，已订阅的客户端会不会跟着改显示名**。矩阵里那一列记的是「添加那一刻」
  的行为（Google 网页 / ColorOS 采用 `X-WR-CALNAME`，Outlook 忽略），而 10-11 下午
  日常产物补上年级后缀之后，**已经添加好的**日历会不会自己变成新名字，没有读数。
  这是一次白捡的观测：下次任何客户端的日历名发生变化时记一笔即可。
- **Outlook.com 在订阅源 404 之后的处置**（是清掉整个日历还是留着残条）。
  演练产物已从分支移除、URL 已 404，Google 那一腿因为用户删掉了订阅而作废，
  只剩 Outlook 这一条还挂着。

## 6. 发布通路的可操作性：`login` 的三处静默失败（v0.6.1 候选，纯本机体验）—— **提示层已落地（2026-10-11）**

**落地范围（commit `6b15f63`）**：三处全部改成会自己说清楚——沿用旧会话时打印
「沿用本地会话（**未验证有效性**）」并直接给出 `login --force` 出口、`cmd_login` 不再说
「会话就绪」、401 与"一个 cookie 都没抓到"两条提示都点名 `--force`、说明里写明这是
【独立的浏览器实例】且这一步要真人完成、中止时补「会话未保存」。
**没有落地的部分**：下面第 1 条提的"廉价会话有效性探测"——它要新增一次网络请求，
而"探测不通"和"会话过期"必须可区分（与 v0.5 三态判定同一个保守原则），风险大于收益，
因此只做了文案层。**这条不是遗漏，是取舍。** 原文保留如下。

订阅通路要长期成立，前提是"每两周能顺利重登一次"。10-11 那次排障里，
`login` 有三处**看起来成功、其实什么都没做**的地方，每一处都足以让人误判方向：

1. **过期会话不触发重登**。只要 home 里存在会话文件，不带 `--force` 的 `login`
   就打印「已检测到本地会话」并退出，不看那份文件是几号的、`fetch` 是不是正在 401。
   **改动面**：`inspect_session` 已经知道 `_saved_at`，让它顺带做一次**廉价的会话有效性
   探测**（学期发现接口单发只读即可），过期时在提示里直接给出「请跑 `login --force`」；
   或者干脆让 `fetch` 撞 401 时把这句建议打在错误出口上（现在只报 401）。
2. **交互式流程无法从后台执行器完成**。它停在终端等一个 Enter，管道里等不到，
   表现是"卡住"，还会留一个占住 profile 目录的浏览器窗口。
   **改动面**：`--timeout` 之类没有意义（要的是真人），能做的是把"请在自己的终端里运行"
   这句话写进交互提示的第一行，并在被 `EOFError` 中止时明确说明"会话未保存"。
3. **"我在浏览器里登录了"与工具会话互不相通**。工具用的是独立用户数据目录，
   用户平时浏览器里的登录态对它毫无作用。这一点 README 已经补了，
   但窗口标题 / 终端提示里最好也带一句「这是独立浏览器实例，请在**本窗口**内登录」。

**代价**：都是提示与判据层面的改动，不动数据通路、不动产物字节。
第 1 条要新增一次网络探测，得保证它失败时**不**把"探测不通"误报成"会话过期"
（与 §7 三态判定同一个保守原则）。

## 7. 托管：GitHub Pages 在免费账户上的硬门槛（决策类，不是代码类）

第 4 条那个"公开分支能枚举 token"的问题，最省事的解法是把发布仓库转私有——
但**免费账户的 GitHub Pages 不能由私有仓库发布**，这是方案层面的死路，不是配置问题。
因此换托管（Cloudflare Pages 一类静态托管）是**零代码改动**的：工具只认 `url_base`，
发布路径本身是普通 git push 到一个只放一个 `.ics` 的分支，换远端就是换个 remote 和 URL。
唯一不能省的先决门槛是**手机关掉代理后能否打开新域名**——打不开就整条链路白换。
具体步骤与回滚记在 `_notes/migration-cloudflare-pages.md`（gitignored，不进仓库）。

## 8. 要不要给"已过原定时刻"的条目也发墓碑（**已回答：不发**，2026-10-13 实测）

**触发点**：2026-10-12 的整学期迁移演练。v1 的 96 条里有 **21 条原定时刻已过**，被 CD10 的
过期筛放掉 ⇒ 它们既不进 live、也不进墓碑，从产物里**彻底消失**。

## 10. 发布恢复凭据的生命周期：为什么必须是两份（2026-10-14 审阅复核后新增）

外部审阅对 P1-02 的 A+ 方案给了一句判词，我认：**「它既承担『已发布状态快照』，又承担
『下一版的发布准备记录』。这两个状态在正常路径看起来相近，但在远端操作结果不确定时有本质
区别。」** 落地后拆成两个逻辑版本（物理上也是两个文件，语义由路径决定）：

| 文件 | 含义 | 何时写 |
|---|---|---|
| `publish-pending-<学期>.json` | 这次**准备发**的完整目标状态 | 推送之前 |
| `publish-journal-<学期>.json` | **已发布凭据**：远端收下过哪一版 | 推送成功之后，由准备稿提升 |

四条由此才成立的性质：

1. **异常不是"远端没推进"的证明。** `publish()` 里 `save_state` 排在 `git push` 之后，
   `git push` 自己返回非零也可能是远端已更新、响应没回来。所以只有"还没执行到 push"
   才允许丢弃准备稿；其余一律留着，交给 `repair` 拿远端字节裁决。
   早先那版"抛异常就退回上一版凭据"会造出最坏的一种状态：远端 B、凭据 A、留底 A、
   `last_push` A —— 四样自洽地错，门与 `doctor` 都看不见。
2. **提升凭据在写本地文件之前。** 反过来一旦死在中间，留底会比凭据新，
   `repair` 拿远端一比对就发现凭据落后、拒绝恢复，只剩人工出口。
3. **`keep` 也要有指纹。** 「这次不该动考试台账」不等于"以后也不检查它"：那份台账
   仍是撤销判定的输入，被删/被改必须能被发现。只记"别动"的话，这一格与审查的场景 2
   （台账静默漏发撤销）是同一类失效。
4. **准备稿还在 = 上一次的结果没裁决 ⇒ 本身就是不相容（`pending_unresolved`）。**
   这一格旧代码是**放行**的：本地四样与已发布凭据（A）逐样自洽，门看不见问题，
   而线上可能已经是准备稿（B）那一版 —— 于是下一次构建拿 A 当 SEQUENCE 与撤销基线，
   正是第 1 条那句"自洽地错"。只有 `repair` 手里有远端真实字节能裁决，
   所以 `push` 与 `doctor` 都不许继续。判定放在 `last_push is None` **之前**：
   第一次发布崩在 `save_state` 时也没有旧版本可对，但那份准备稿同样是"远端可能已推进"的信号。
5. **发布路径只能有一条事务。** `push` 与 `rotate` 的补发共用同一段代码（准备稿 → 推送 →
   提升凭据 → 回写本地四样），相容性那道门也只有一处。2026-10-15 审阅的 P0-01 就是这条
   被破坏的形态：rotate 自己调 `publish()` 再回写留底，凭据不跟着换 token，
   于是**正常**换 token 之后的每一次 `push` 都被自己的 `journal_token` 拦死。
   推论两句：①"在 rotate 结尾补写一份快照"**不算**满足这条——那解决不了"推送成功、
   本地写失败"的窗口，必须让准备稿先落盘；②门要排在**换 token 之前**，先停手才留得住
   旧 URL 这条退路（唯一的例外是留底根本不在场：那一支不构建不发布，但未裁决的准备稿
   仍然要先裁决，因为换 token 会让两份凭据统统变成旧 token 的、`repair` 从此无从下手）。
6. **旗标的放行范围是一份白名单，不是"所有不相容"。** 强行继续若会销毁裁决所需的证据，
   就不该被同一个旗标覆盖（`pending_unresolved`、`journal_invalid`）。见下面 P1-02。

### 已接受的取舍（不是待办）

- **T2：push 成功、`save_state` 之前崩。** 同字节会多发一次提交（`cal` 仍是孤儿单提交，
  `rev-list` 计数 1，不涨历史）。实测读数见 `_notes/drill-085/probe-edges.py`。
  接受它，好过把"远端不确定"当"远端没动"。
- **凭据损坏 = 拒绝，不降级。** "从没写过"（旧版本升级）可以走弱判据；"写过但读不懂"
  不能——那等于让一份损坏的校验文件触发更宽松的校验。
- **`keep` 的内容补不回来。** `repair` 收尾会再跑一遍同一判定并如实报错，
  不许把"无法恢复"说成"已与线上一致"。

### 已裁决的口径（2026-10-15）

- **`doctor` 把"本地发布状态散架"算阻塞项，不是警告**：凡 `check_local_compatibility`
  不通过（含上面第 4 条那一格），「订阅」项判 `fail` ⇒ 退出码 `5`；不新增退出码
  （`push` 继续用业务错误 `7`，两个码不必相同）。原则一句：**门会拦的状态，
  体检不许只留一行警告**，否则用户要等到真发布才发现自己需要 `repair`。
  两条边界同时定下：①「没有凭据、但留底与最后一次发布逐字节相符」那一格**留在警告**
  （`push` 在这格是放行的，体检不能比门更凶）；②`doctor` 保持纯本地只读，
  只**提示** `repair`，不代跑 fetch、不代改任何文件。
- **P1-02：旗标按 reason 收窄。** 判据不是"用户想不想强行发布"，而是"强行继续会不会
  销毁裁决所需的证据"。白名单：`no_journal` / `journal_token` / `journal_sha` /
  `journal_branch` / `baseline` / `course_ledger` / `exam_ledger` / `*_keep` / `uid_recipe`；
  白名单外（`pending_unresolved`、`journal_invalid`，以及今后新增的任何 reason）一律不放行。
- **P1-03：快照自洽性在"读"这一层判死。** `sha256(ics_text) != ics_sha256`、台账 Base64
  严格解码不过、关键字段为空 ⇒ 直接 `JOURNAL_INVALID`，恢复写盘一个字节都不发生。
  这条不是洁癖：`base64.b64decode` 默认**丢弃**非法字符（`"!!!"` → `b""`），坏掉的台账
  字段会"成功地解码成一份空台账"，照着恢复等于静默清空撤销历史。
- **P1-04：`keep` 的完整陈述是"内容指纹 + 在不在"。** 指纹为 `None` 是有意义的读数
  （"当时这份文件不存在"），不是免检通行证。
- **P1-05：凭据与「上次发布记录」交叉核对补齐哈希与分支。** 两格现有崩溃序列走不到
  （`pending_unresolved` / `journal_token` 先接住），能到的是手工改动与今后新增形态：
  按 fail-closed 收下，但**不写成可达缺陷**（AGENTS.md 红线 3 的同一条纪律）。
- **P0-01：`repair` 拿远端裁决时，文件名与字节一起看。** 字节平票时用
  「tip 上那个文件名属于哪一份凭据」破平——rotate 的补发经常内容一字未改、只换文件名。

### 仍欠的

- **多学期并发**：两份凭据按学期分文件，但同一 home 里两个学期同时 push 的相互影响
  没有用例。低概率（串行 CLI），先记不修。

## 11. 三处小加固的取舍（2026-10-15，P2-03 / P2-04 / `_WEU`）

这三条都不改产物，改的是"失败时留下什么现场"，所以判据统一成一句：
**失败要么什么都没动，要么留下的仍是可用状态。**

- **P2-03：发布分支只提交那一个 `<token>.ics`。** 原先的 `git add -A`（不带 pathspec）
  把发布工作目录里的任何残留都推上**公开**分支，而远端 tip 那道 tree 护栏只看
  "进来之前长什么样"，看不见"这次要发出去的东西长什么样"。取舍是**清空索引 + 只加一个
  文件 + 提交前核对**，而不是"把多余文件删掉"：工具不许顺手删用户目录里的东西。
  副作用是 rotate 的"旧文件从 tip 消失"由"删除也要入索引"变成"索引里根本只有新文件"，
  更彻底；`test_publish_still_replaces_the_old_token_file` 专门钉住这一点没被弄坏。
  实测：改动前 `ls-tree` 真会多出 `私人笔记.txt` 与 `nested/scratch.log`。
- **P2-04：`save_raw` 的轮转改成复制优先。** 旧顺序 `current → prev` 是 move，
  新内容写失败时当前路径为空（`load_raw` 直接报没有缓存）。新顺序：序列化 → 复制旧内容到
  `.prev` → 原子覆盖当前。
  ~~接受的小退化：新内容写失败时 `.prev` 会与 `.current` 同内容~~ —— 这一句已被同日的
  **P2-01** 取代，别再照它理解现在的行为：轮转现在排在**新内容落盘之后**（旧内容先在内存
  里拿着），写失败时连 `.prev` 都不动。
- **P2-01：三代快照用例把顺序再改一次。** 复制优先救回了"当前文件不会消失"，但轮转排在
  写盘之前仍会让一次写失败**少掉一整代历史**（`.prev` 上的 A 被 B 冲掉），`diff` 的比较
  基线退化成"和自己比"。审查建议先测再改，实测读数正是改动前 `.prev` 从 A 变成 B。
  新顺序留下的窄缝是"新内容已落盘、写 `.prev` 又失败"⇒ 当前是新的、`.prev` 是上上代：
  保留较旧但可读的一份，好过为了对齐先毁掉它；没有为此引入暂存文件或回滚机制（YAGNI，
  一代 `diff` 基线的用途只是比对，不需要三代可恢复性）。
- **`_WEU`：承重判据与条数判据分开报。** 消融实验（2026-10-14）说得很清楚：
  只去掉 `_WEU` 就 403，两份同名 `JSESSIONID` 少任一份仍 200。所以
  ①**不**把判据收紧成"非 `_WEU` 不算登录走完"（`/jwapp` 条数仍是主判据，收紧会造成
  新型误拦），②也不把 403 归因回同名 cookie 的取舍（那条已被实测否定）。
  新增的只是"条数够却没有票据"这一格的可见性：`login` 收尾那句与 `doctor` 各自说清，
  都是**警告**而非阻塞——那份课表快照仍然可以导出。

## 12. 要不要把撤销条目"搬到过去时段"，让它在忽略 `STATUS` 的客户端上不可见（**待评审**，2026-10-15 新增）

**触发点**：v0.8.0 的 UID 迁移发布之后，正式订阅（ColorOS 系统日历）第一次露出占位——2026-10-15
16:10–18:00 那条「已取消的活动」与照常要上的一门课 1:1 撞在同一时段。用户当场确认**单条删不掉**、
**「删除订阅」不带走本地事件**（见 §8 补记）⇒ 手机侧三个清理动作全部否证，剩下的唯一杠杆是
**改写它**而不是删除它。

**现状证据**（实测/实读，不含推测）：

- §8 早就记下一条**反向可用**的观察：10-12 演练里那 21 条"从产物彻底消失"的旧条目虽然删不掉，
  但**都落在过去的时段，日常视图里看不见，属于脏但不挡路**。本议题就是把这条既有观察当工具用——
  既然删不掉，就把撤销条目的 `DTSTART`/`DTEND` 写成一个**已过去且恒定**的时刻，让它不再进入
  今天/本周视图。
- 字段来源只有一处：`cancellation.build_cancellation_events()` 现在**逐字复制**台账条目的
  `start`/`end`（D2/§5 的既有决策，本议题只推翻"时刻"这一半，不推翻 UID 照抄、固定标题、
  零 `LOCATION`/`DESCRIPTION`）。考试与课程两支共用同一函数 ⇒ 一处改动覆盖两支。
- ColorOS 会**整体替换**同一 UID 的字段（10-10 与 10-12 两次真机读数：标题被原地改成
  「已取消的活动」、`LOCATION` 被清空）⇒ 按同一机制，时刻也会被搬到新值。但**"改时刻"这一格
  从来没人验过**，这是本议题的主风险，见前置条件 P2。
- `sequence.event_fingerprint()` 的输入含 `start`/`end` ⇒ 搬家那一次发布 `SEQUENCE` 会 **+1**，
  之后因为新时刻恒定而不再漂移（与固定标题那条不变量同理：内容恒定 ⇒ 重渲染字节相同）。
- 撤销条目**不受 `--from-date/--to-date` 裁剪**：代码顺序是先裁 `events`/`exam_events`
  （`exporter.py:947-952`）、之后才 `_append_cancellation_events()`（`:1235` 课程支、`:1258`
  迁移支）⇒ 搬到过去不会被一次局部导出剪掉。
- 只改时刻、**不改台账里的真实 `start`** ⇒ `cancel_candidates` 的过期筛照旧按原定时刻退场
  （本学期最晚一批到 2027-01-02）。携带窗口一天不缩短 ⇒ **迟到同步的客户端仍在自己窗口内收到
  这条 CANCEL**。这正是它比"摘除墓碑"强的地方。
- 门 2 不受牵连：分子分母都只数 UID 集合（`mass_cancellation_check` + `upcoming_ledger_count`
  的 `exclude_uids`），搬家不改候选集，也不改 `already_cancelled` 的口径。

**否证掉的替代方案（别再去做）**：从课程台账 `subscribe/last-courses-<学期>.ics` 里摘掉那批墓碑
UID、发一版"纯 live"产物。取证：该台账此刻是 168 条 = 96 live + 72 墓碑，而**墓碑与活课在台账里
同形（D10 不写 `STATUS`）**，摘错一条就是撤掉一门真课；更关键的是本地行已经在手机上（10-12 演练
是整本一次导入、占位与 live 1:1 全量落地），**产物消失 ≠ 本地消失**（§8 已实测，**但那条结论的
前提是 ColorOS 原生订阅——ICSx⁵ 那条通路上 prune 会真删，见 §13**），所以这一刀换不到
任何清爽，反而对没同步到的认 `STATUS` 客户端永久放弃这次撤销——让它们留下**带真实课程名**的 v1
旧课表，比占位更糟。

**改动面**：`build_cancellation_events()` 增加一个"搬家时刻"入参，由调用方按学期算出一个
**恒定、可复现、不含任何个人信息**的过去时刻（例如学期首日前一天 00:00，`DTEND` 保持原时长）；
`exporter` 两处调用点传参；两支 golden 各变一次字节（搬家那次 `SEQUENCE` +1）；
`tests/test_cli_cancellation.py` 等带撤销断言的用例按新口径复核；v0.8 规格 §5/§11 与本备忘 §8
里"D2 起止逐字复制"的措辞要就地标注被推翻的范围。

**前置条件（必须先验，不许先写代码）**：

1. **P1｜Google 网页版**：一条已导入的 `CONFIRMED` 事件，收到**同 UID、`STATUS:CANCELLED`、
   但 `DTSTART` 与本地不一致**的更新 ⇒ 是否仍按 UID 移除？现有实测（v0.6 小规模、10-13 的 5/5 全清）
   全部是时刻一致的场景。RFC 5546 的 CANCEL 主要认 UID，但这一格我们没验过 ⇒ 未验前文档一律写
   「通常会」。
2. **P2｜ColorOS**：同 UID 的 `DTSTART` 改写是否被"整体替换字段"搬到过去时段。机制与 10-12 同形，
   缺的正是"改时刻"这一格。
3. **P3｜Outlook.com**：忽略 `STATUS` 的第三条腿，搬家对它等于"把那门课改到过去的日期"——
   可接受，但要如实记录，别写成"清理"。

演练照 v0.6/v0.8 的规矩：一次性 token 的隔离 URL（`XLJFZ/calendar-drill` 那一套试验田）、
合成身份字段 + 真实时间骨架、产物用后即删，结论回写本节与 §8。

**代价 / 开放问题**：

- 一学期的占位会**堆在同一个过去日期**上，翻到那天能看到一坨「已取消的活动」。可选缓解是按 UID
  散列到学期首日前的若干天，但那是为了让日志好看而增加不可复现性——等 P1/P2 通过再判值不值。
- 库里行数**一条不减**。收益只有"不再进入可见视图"，§8 那句「脏但不挡路」的口径继续成立。
  所以本议题买的是观感，不是清理；写文档时不许把它描述成"解决了残留"。
- 真实退课的占位同样受益（不再与某门课撞同一时段），但它的可见期本来就到原定时刻为止——
  搬家换来的增益主要体现在**迁移/整学期**这种规模上。
- 一次性 vs 长期开关：迁移只剩这一次（换学期时旧条目全部已过期 ⇒ 天然零墓碑，见 §8 的过期筛），
  所以真正长期吃到收益的是**未来那些学期中途的配方变更**。若因此判定"为一次已发生的事改协议语义
  不值"，那就是**不做**——本议题的正确出路包括"评审后关掉"，别为了有个 §12 而硬做。
- 版本号：改的是已发布产物的形态，走 0.8.x 还是 0.9.0 等排期时按"用户可见产物变化"的口径定，
  本议题不预判。

## 13. Android 侧统一到 ICSx⁵（**方向已拍，读数待补**，2026-10-15）

**决定**：Android 用户的首选订阅通路改为 **ICSx⁵**（包名 `at.bitfire.icsdroid`），不再按 ROM 各家
去摸系统自带入口；ColorOS 的「URL 日历」**保留为免安装备选**（不删——"不想装第三方 App"是真实
需求）。拍定理由由用户给：统一，别让每个 ROM 各自摸索。

**为什么值得统一**（逐条标证据强度；除注明外全部是**上游源码取证，真机未验**）：

- **消失项会被真删**：`ProcessEventsTask.processEvents()` 每次成功同步末尾无条件
  `calendar.retainByUID(uids)`，把本地 UID 不在本次源里的行以 sync-adaptor 身份硬删，
  **没有开关、默认就是 prune**。这正是 §8 那格在 ColorOS 上最缺的一半。
- **`STATUS` 不被丢弃**：它依赖的 ical4android 在 `AndroidEvent.buildEvent()` 里把
  `Status.VEVENT_CANCELLED` 映射成 Android 的 `Events.STATUS_CANCELED` 落库。⇒
  "撤销条目被显示成普通日程"这个问题从**通路侧**挪到了**日历 App 侧**，而后者是可换的。
- **维护面收敛**：行为矩阵里"各家系统自带入口参差"（MIUI / 鸿蒙常只给一次性导入）这一整格，
  从此由一个上游承担，N 个 ROM 收敛成 1 条通路。
- 开源、单 APK：仓库 https://github.com/bitfireAT/icsx5 ，GPL-3.0，实测最新 release
  `v2.4.3`（2025-12-16，唯一产物 `icsx5-92-2.4.3-standard-release.apk`，16 MB）。官方
  https://icsx5.bitfire.at/privacy/ 写明「ICSx⁵ won't send event data to anywhere」、
  不统计不跟踪。

**分发成本（这才是真门槛，写用户指引时必须排在好处前面）**：Google Play 版按我方既有口径是**收费**
的（这格 10-15 未复验，以商店实际为准）；F-Droid 免费但要先装第三方商店；GitHub 直下 APK 需要
"允许未知来源"。而本机 10-15 实测 `curl github.com` 返回 000、`f-droid.org` 不可达
⇒ **手机侧下载环节在国内网络里大概率要挂代理**。README 那句"三步上手"对 Android 实际是五步。

**源码上看不出能解决的（本轮已有一条真机读数与之冲突，别当结论）**：**单条删不掉**。
ICSx⁵ 建的日历写的是 `Calendars.CALENDAR_ACCESS_LEVEL = CAL_ACCESS_READ`，而 DAVx⁵ 手册把后果
说得很直白——只读日历里 App 不能 create/modify/**delete**；且它的数据库只有 `Subscription` 与
`Credential` 两张表，**没有任何"用户删过"的记录**，同步分支是 `queryByUID` 为空就重新 `add()`
⇒ 据此推"强删的条目下次同步必被加回"。**但 2026-10-15 的初步真机读数是"能删、且观察未回来"**，
与本段的推论直接冲突——见下面读数补记第 2 条：这条读数缺"被删那条的原定时刻是否已过"的对照，
**在对照取到之前，本段只算源码侧的推理，不算实测结论**。真要做到"本地删了就永久删"且无需对照，
只有 DAVx⁵ + 一台真 CalDAV 服务器（手册明确有 locally-deleted → HTTP `DELETE`），
代价是放弃"静态整本重发"这套架构，**不在本议题范围内**。

**别把希望押在 DAVx⁵ 上**：https://github.com/bitfireAT/davx5-ose/issues/439 （2023-10 开、
2026-02 仍 open）说 Webcal 订阅"路线图上有、但没有 ETA"，而手册里 DAVx⁵ 遇到 Webcal 集合是
**把 URL 转交给 ICSx⁵**，它自己不拉纯 HTTP 的 `.ics`。长期看 ICSx⁵ 大概会被取代，但那是"入口搬家"，
判据与产物形态都不变——我们文档已经钉过「是 ICSx⁵ 不是 DAVx⁵」这条，指引别倒退回去。

**必须先取的真机读数（拿不到就不许把上面任何一条写成实测）**：用户 2026-10-15 已把正式订阅同时
订到 ICSx⁵、并在 ColorOS 里隐藏旧那本，所以下面几条这学期就能收到。

1. **canceled 到底显不显示**：产物里那 72 条墓碑在 ICSx⁵ 这本日历中是隐藏、当普通日程显示、还是
   显示成"已取消"。判据必须把**库里**和**界面**分开：用
   `adb shell content query --uri content://com.android.calendar/events --projection _id:title:status`
   看那条的 `status` 是否与普通事件**不同**——**不许照抄任何"等于几"的数字**，官方源码只给了符号
   常量 `Events.STATUS_CANCELED`，整数值本项目没有核实过。库里对而界面错 ⇒ 换日历 App 可解，
   架构一字不动。
2. **prune 在 GitHub Pages 上是否真生效**：ICSx⁵ 走 `If-None-Match`/`If-Modified-Since`，服务端回
   304 时它一个字都不重读 ⇒ 要确认 Pages 的 `ETag`/`Last-Modified` 随发布变化；不变则用户侧兜底是
   "手动同步（忽略缓存）"。天然探针：10-16 那天 1 条占位与 1 门真课同时段，看这本显示几条。
3. **隐藏旧那本之后视图是否真单份**：两本的 live UID **完全相同**（token 不进产物，UID 只由
   学期/课程号/星期/节次决定）⇒ 跨日历会不会"改一条动两条"，未验。
4. **只读旗在 ColorOS 上的实际表现**：点开 ICSx⁵ 的一条事件，看有没有删除入口、报错文案是什么。
5. **URL 暴露面**：官方 privacy 页自己警告「calendar URLs are accessible for other apps」——URL 会
   作为 `Calendars.NAME` 写进 provider，任何有日历权限的 App 读得到。与 §4 的 token 公开面、与
   托管迁移（转私有仓）一并评估。

**读数补记（2026-10-15 当天，正式订阅 + ICSx⁵，用 ColorOS 自带日历显示；单账户单样本）**：
上面清单里的第 1、4 条当场有了答案，外加一条不在清单里的日历名读数。其中**两条把我先前的
源码推论打掉了**，如实记下来：

1. **第 1 条｜canceled 不过滤**：那 72 条占位在 ICSx⁵ 这本里**照旧显示成普通日程**。
   换通路只把问题从同步侧挪到显示侧，观感一字没变。这条**不否证**源码那条映射
   （库里到底落成什么状态值没取 adb 读数），它否证的是后面那一步期望——
   "映射成 canceled ⇒ 界面就看不见"。⇒ 想靠换通路让占位消失，此路不通。
2. **第 4 条｜单条能删，且观察未回来** —— 这与我据源码下的**确定结论**直接冲突
   （我以为 `CAL_ACCESS_READ` 只读 + 没有"用户删过"的记录 ⇒ 删不动、下次同步必被
   `queryByUID` 加回）。**但这条读数还不能当结论用**：缺一个对照——被删那条的
   **原定时刻究竟已过还是仍在未来**。若已过，"没回来"只是产物退场加上 prune 的共同作用，
   与"尊重本地删除"无关；若时刻还在未来而它没回来，才是本地删除真被尊重、源码那条推论被否证。
   **对照取到之前这一格一律写"未定"**，两边都不许落成事实。
3. **清单外｜日历名**：没让手填，直接就是产物给的课表名 ⇒ 矩阵那一格可以写实测「是」。
4. **第 2、3、5 条未取**：prune 是否被 Pages 的 `304` 短路、双本同 UID 会不会互相干扰、
   URL 落进 `Calendars.NAME` 的暴露面——都还是空的。用户当天的总体反馈是"用着很好很方便"，
   但这句是体感，不构成上面任何一格的读数。


**读数补记（2026-10-16，只测服务端，零发布、零写盘）**：第 2 条的**服务端那一半**当场有了答案，
另外两件事被顺带证实是"取不了"而不是"没去做"。

1. **第 2 条（服务端一半）｜Pages 的条件语义成立，而且 `304` 是校验元驱动的**。对线上那份 `.ics`
   （65165 B、sha256 前缀 `5b695bd19bcfd5ea`，与 UID 迁移发布时记录的线上字节一致）做了**带控制组**的
   条件请求：首次 GET 回 `200` + `ETag: "6ad064b2-fe8d"` + `Last-Modified: Thu, 15 Oct 2026 05:29:22 GMT`
   + `Cache-Control: max-age=600` + `X-Cache: HIT`（`Age` 39–41）；`If-None-Match` 单用、
   `If-Modified-Since` 单用、两者同用 ⇒ **三次全部 `304` 且响应体零字节**；控制组换一个假 ETag ⇒
   `200` + 完整 65165 B。ETag 尾段 `fe8d` 十六进制就是 65165 = 字节数 ⇒ 它是内容派生的。
   **能写到什么程度**：条件请求会命中 `304` 这件事**已实测**（这条正是"prune 可能被 304 短路"的
   前提，此前只有源码侧推理）。**不能写到什么程度**：①"内容变了会不会拿到新字节"由控制组保证 = 会，
   但**发布前后 ETag 的真实对照**仍未取——那需要一个已授权的发布窗口，**本次没有为了造一次变化而发布**；
   ②"ICSx⁵ 拿到 200 之后是否真的执行 `retainByUID`"是 App 侧行为，服务端证不了。
   ③ `max-age=600` 加上 `X-Cache: HIT` 通常意味着十分钟内重复请求可能由边缘直接给缓存副本，
   但这只对"缓存语义"成立，**未对 ICSx⁵ 实际请求序列取证**，别当读数用。
2. **第 1、3、5 条这次一个都取不了，原因是工具而不是判断**：本机没有 `adb`（不在 PATH，
   `%LOCALAPPDATA%/Android/Sdk/platform-tools/` 与 `C:/Android/Sdk/platform-tools/` 两处默认路径都不存在，
   `scrcpy`/`fastboot` 亦无）。这三条的"库里"那一半都要读日历 provider，装 platform-tools +
   手机端授权 USB 调试是前置；而 `adb shell content query` 在 ColorOS 上放不放行**本身也未验**，
   装上先探一次再说。
3. **第 4 条的对照卡在事实而不卡在工具**：要判"被删那条的原定时刻是已过还是仍在未来"，
   得先确认 10-15 当天删的**究竟是哪一条**——这件事只有用户本人知道，问一句就能定，
   不需要 adb、也不需要发布。
4. **不过第 4 条的对照不必等那条历史读数——线上现在就有未来时刻的占位**（10-16 实测，只读、
   零发布）：把线上那份 `.ics` 折行还原后逐条解析，`STATUS:CANCELLED` 共 **72 条 = 原定时刻仍在未来
   70 条 / 已过 2 条**，最晚一条排到 **2027-01-02 08:00**，全部 `SEQUENCE:1` 且**没有 `RRULE`**
   （每条都是独立的单日块，不是带规则的母事件）。更关键的一点：**这 70 条未来墓碑每一条都能在
   同一个 `DTSTART`+`DTEND` 上找到一条 live 事件** ⇒ "占位挂在真课的同一时段上"不是 10-15 那一天的
   巧合，而是接下来整个学期的常态（这条同时把下面"与 §12 的关系"那句依据钉实了）。
   ⇒ 于是这一格**不用 adb、不用发布就能取**：删掉一条时刻仍在未来的占位、手动同步一次、
   看它会不会被 `queryByUID` 加回。没回来 = 源码那条"只读 + 无删除记忆"的推论被否证；
   被加回 = 源码成立，而 10-15 那次"能删"只是因为它时刻已过。
   **这条探针是设计出来、还没跑过**——跑完之前两边都不许写进规格。

**与 §12 的关系（读数是反着来的，别照旧口径理解）**：我先前在这里写"prune 若成立，
§12 多半可以直接关掉"。第 1 条读数出来之后这句话**站不住了**——prune 处理的是"已经从产物里
退场的条目"，而占位之所以刺眼是因为它**此刻还挂在真课的同一时段上**，那批条目仍在产物里、
prune 一条也碰不到。所以 §12「搬到过去时段」的收益不但没缩，反而被这条读数**加了回来**：
它治的是"当下这一格"，prune 负责"到点之后真的删干净"，两者互补而不是替代。
**§12 的状态改为：不要因为换了通路就关掉；先做上面那个对照探针 + 隔离演练验 P1，再定实现形态。**

**发布位置**：等第 1、2 条读数回来，再改 README 的「三条最要紧的口径」与
`docs/user-guide/subscription.md` 的客户端矩阵，并同步 skill 的 `references/client-matrix.md`。
在那之前，用户指引只写"Android 首选 ICSx⁵ + 免安装备选 ColorOS"，**不写**任何未验的行为断言。
