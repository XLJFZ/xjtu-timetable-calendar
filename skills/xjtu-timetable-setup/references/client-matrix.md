# 怎么选订阅客户端（决策版）

矩阵全表在 README。这里只回答"用户提了这个诉求，该选哪条路、为什么"。

## 「我要它自己更新」

必须是**订阅型**入口。分辨方法很简单：订阅型入口带「上次同步时间」，
导入型只有显示开关。

- **Google 日历**：只有**网页版**能订阅（左侧「其他日历 → 通过 URL 创建」）。
  手机 App 里既没有订阅入口，也**不显示** URL 导入型日历——别在 App 里找。
- **Outlook.com**：网页版「添加日历 → 订阅日历」，但对话框会强制你手填日历名，
  产物里的 `X-WR-CALNAME` 它不采用。
- **ColorOS 系统日历**：自带「URL 日历」订阅入口（我的 → 添加日历 → URL 日历），
  会定期回源并**原地更新**已存在的事件，日历名直接采用 `X-WR-CALNAME`。
- **其他国产 ROM**：用 ICSx⁵ 做 URL 订阅。注意是 **ICSx⁵**，不是 DAVx⁵
  （后者只做 CalDAV，没有 URL 订阅入口）。给同步器关掉电池优化并允许自启动，
  否则后台查杀会伪装成"装了但不更新"。
- **一次性导入**（Apple 日历双击 .ics、各家"导入日历"入口）：一次性快照，
  之后 push 多少次都收不到。用户如果只接受手动导入，就要明确告诉他每次都得重导。

## 「多久会更新」

三家实测都**不是实时**，而且**都不能从客户端强制刷新**：

- Google 网页：两次实测 ≤3h31m、≤10h05m（官方只说"最长约 24 小时"）。
- ColorOS：实测 ≤2h35m，能原地更新。
- Outlook.com：添加时立刻拉一次，此后实测 **14 小时以上未再回源**（官方口径约每 3 小时）。

用户催"怎么还没变"时，先报这个区间，再确认他改的那份**确实发布出去了**
（`doctor --verify` 的 URL 自检 + `subscribe status` 留底一致），别急着怀疑客户端。

## 「取消的考试怎么还在」

三种结局，取决于客户端：

1. **删干净** —— Google 网页版实测会移除带 `STATUS:CANCELLED` 的日程。
2. **留一条「已取消的活动」** —— Outlook.com 与 ColorOS 实测**忽略**该字段，
   把撤销条目当普通事件导入。v0.6.1 起它带固定标题，所以一眼可辨；
   但它**不会自己消失**，要等原定时刻过去、条目从产物里退场。
   「退场后客户端会不会顺手清理」**尚未验证**，别承诺会清。
   订阅型日历通常是只读的（Google 侧已确认没有"删除单条事件"的入口）。**别指望退订重加清得掉**：
   2026-10-12 整学期迁移演练实测，这条占位是**产物自身携带**的 `STATUS:CANCELLED` 事件，忽略该字段
   的客户端重加时会**再导入一遍**（重加后占位仍在、仍与新日程 1:1）。退订重加只能清本地重复项，
   清不掉占位——占位要等各自原定时刻过去后由下一次发布收掉。
3. **完全不动** —— 一次性导入型不回源。

## 「日历名不对」

名字来自产物的 `X-WR-CALNAME`，而客户端**通常在"添加"那一刻取一次**就不再更新：
Google 网页与 ColorOS 实测采用它，Outlook 忽略并强制手填。
产物后来改了名，**已添加的日历未必跟着变**——退订重加**通常**有效，
不重加会不会自己改名尚未验证。（2026-10-12 整学期迁移演练里，ColorOS 上"删除日历后重新添加"
**保留了旧事件**，说明该客户端的重加未必等于拿到一份全新数据，这条处置尚未在那台机器上复验。）
