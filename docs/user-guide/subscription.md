# URL 订阅（subscribe）

这份文档讲使用层面的细节，从 README 拆出来以保持主入口简短。

> 从 README 拆出，内容一致；主入口见 [../../README.md](../../README.md)。

## URL 订阅（subscribe）

「快速开始」的交付方式是「拿到文件 → 手工导入」：课表一变就要重新导出、
重新导入，多端各来一遍。`subscribe` 增加一条 **URL 订阅通道**——把同一份 .ics
发布到**一个只有你知道地址的静态 URL**（GitHub Pages 或私有仓 + Cloudflare Pages，
二选一，见下面「先选一条托管路」），日历客户端按 URL 订阅；
之后每次课表调整只需本地跑一次 `subscribe push`，客户端自动拉取，不再需要导入。

> **口径先说清**：刷新是**纯手动**的——本工具不做定时任务、不常驻进程，
> 也不会替你 `fetch`。「手机 24 小时内自动呈现新状态」的前提是你自己 push 过。
> 一个学期一个 token、一个订阅 URL；多学期合并进同一 URL 是明确不做的事。

### 先选一条托管路

两条路的产物、命令、token 机制**完全相同**，区别只在「谁来把这个分支对外服务」：

| | 路径 A：GitHub Pages | 路径 B：私有仓 + Cloudflare Pages |
| --- | --- | --- |
| 设置耗时 | 五分钟 | 十几分钟，且要注册一个第三方账号 |
| 「知道 URL 才能读」这条保护 | **不成立**：仓库必须公开，分支文件列表页匿名可读 | 成立 |
| 国内可达性 | 实测可通（多条真机读数支撑） | `pages.dev` 国内**间歇**可达，上线前必须在手机上验一次 |
| 是否免费 | 是 | 是（免费档，不需要信用卡） |

想省事选 A，想守住订阅地址选 B。**先按 A 走完、之后改 B 也完全可以**：
换托管只改状态文件里 `url_base` 一个字段，token 全程不换。

### 路径 A：GitHub Pages（一次性设置）

1. 在 GitHub 建一个**公开**仓库（例如 `cal-alice`）。它里面只会出现一个
   `<token>.ics` 文件。
2. 开启 Pages：仓库 Settings → Pages → **Deploy from branch**，
   分支选 `cal`、目录选 `/(root)`。
   （`cal` 分支由首次 `subscribe push` 创建；下拉里选不到它时，先完成下面
   两步再回来开启，顺序不影响结果。）
3. 登记发布目标，生成 token：

   ```bash
   python -m xjtu_calendar subscribe init --repo https://github.com/<用户名>/cal-alice.git --semester 2026-fall
   ```

   init 会打印订阅 URL 和上面那条 Pages 指引。GitHub 远端的 URL 前缀自动推导；
   非 GitHub 远端必须用 `--url-base` 显式给出公开访问前缀，否则 init 直接拒绝。
   每学期一个状态文件（`subscribe/subscribe-<学期>.json`），重复 init 会报错，
   重新登记需先删除该状态文件（换新 token）。
4. 发布第一版：

   ```bash
   python -m xjtu_calendar subscribe push --semester 2026-fall
   ```

5. 把订阅 URL 复制到日历客户端（入口见下）。Pages 首次生效有数分钟延迟，
   可运行 `subscribe status --verify` 对 URL 做一次匿名 GET 自检。
   iOS / macOS 用户还可直接打开 init 一并打印的那条 `webcal://` 链接
   （口径与手动路径见下面「iOS / macOS：`webcal://` 订阅链接」）。

### 路径 B：私有仓库 + Cloudflare Pages

路径 B 的产物和命令与路径 A 完全一样，只是对外服务换成了 Cloudflare，
这样发布仓库就可以是**私有**的。步骤：

1. 在 GitHub 建一个**私有**仓库（例如 `cal-alice`）。
2. 登记发布目标。**`--url-base` 这一步不能省**，而且要先想好 Cloudflare 的项目名：

   ```bash
   python -m xjtu_calendar subscribe init --repo https://github.com/<用户名>/cal-alice.git --url-base https://<项目名>.pages.dev/ --semester 2026-fall
   ```

   不带 `--url-base` 的话，工具见远端是 GitHub 就自动推导成
   `https://<用户名>.github.io/<仓库>/` —— 私有仓上 GitHub Pages 不提供托管，
   那条地址是 404，而 init 不会为此报任何错。
   另外：**init 收尾会无差别打印一条「一次性开启 Pages（GitHub）：仓库 Settings → Pages →
   Deploy from branch」**，它只对路径 A 成立。走路径 B 时那两行直接忽略——你的仓库是私有的，
   GitHub Pages 那项要么灰着要么开了也不服务；对外服务由下面第 4 步的 Cloudflare 项目负责。
   （该文案目前不区分托管路，是已知待修项，见 `docs/design/2026-10-11-subscription-followups.md` §14。）
3. 先发布第一版（这一步创建 `cal` 分支）：

   ```bash
   python -m xjtu_calendar subscribe push --semester 2026-fall
   ```

   **建议先 push、再去 Cloudflare 建项目**：建项目时要当场选生产分支，而 `cal` 分支
   是这次 push 才创建的。分支还不存在时那个选择框会怎样（列不出来？还是允许手填？）
   **没有实测过**，按这个顺序走就碰不到这个问题。
4. 注册 Cloudflare（免费档）→ Workers & Pages → Create。
   ⚠️ **落到的那一页上五个选项（Connect GitHub、Connect with GitLab、Start with
   Hello World!、Select a template、Upload your static files）全是 Workers 那条路**，
   发出来的域名是 `*.workers.dev`，在国内基本不通，而且不会有任何报错告诉你为什么。
   Pages 藏在这页**最底下那行小字**里：**"Need to use the legacy Pages workflow?
   → Continue to Pages"**。点它，再选 **Import an existing Git repository**
   —— 不要选 Drag and drop your files，那是手工上传，会断掉「push 即自动发布」这条链。
5. 授权 GitHub 时把范围改成 **Only select repositories**，只勾这个发布仓库。
6. 四项配置：Production branch = `cal`、Framework preset = **None**、
   Build command **留空**、Build output directory = `/`。Save and Deploy，
   等那条 deployment 变 Success（不跑构建，当天实测几分钟内就完成）。
7. **先验可达性，再订阅**：手机**关掉 VPN / 代理**，用浏览器打开
   `https://<项目名>.pages.dev/<token>.ics`，Wi-Fi 与移动数据**各测一次**，
   看到以 `BEGIN:VCALENDAR` 开头的内容才算过。打不开就别把订阅地址换成它 ——
   `pages.dev` 的可达性在国内是间歇的，而这条通路是手机自己去拉的，没人给它挂代理。
8. 之后与路径 A 完全相同：`fetch` → `subscribe push`，Cloudflare 随每次 push 自动重新部署。

**只有一个时点会重新踩上面第 2 步那个坑：下学期第一次 `init`。**
它漏了 `--url-base`，工具打印出来的就是一条 404 的 github.io 链接，且不报错。
**`rotate` 不在这个列表里**（2026-10-22 对着代码与离线旅程复核）：`rotate` 既不接
`--url-base`，也不重新推导地址——它照状态文件里已有的 `url_base` 换新 token 再补发，
所以只要 init 那次没漏，rotate 就不会把路径 B 的订阅指回 github.io。
漏了 init 也不用重做 init：手工把状态文件 `subscribe/subscribe-<学期>.json` 里的 `url_base`
字段改成 Cloudflare 那个前缀，再用只读的 `subscribe status` 确认即可。
**不要**为了「验证一下」去跑 `push`：换地址本身不需要发布，而隔了几天再 push，
课表已随日期变化，等于发出一次你并不想发的新版本。

**两条路的一处已知差异**：GitHub Pages 的响应同时带 `ETag` 和 `Last-Modified`，
Cloudflare 只带 `ETag`、不发 `Last-Modified`。带 `If-None-Match` 的条件请求在两边都实测过，
都能命中 `304`、不重复拉全文（ICSx⁵ 按上游源码会带这个头，本项目未对它的实际请求序列取证）；
只认时间的客户端在 Cloudflare 这边每次都会拿全文，功能不受影响，只是多花流量。

**换回路径 A**：把仓库改回公开，GitHub Pages 随之恢复；token 没换 ⇒
把 `url_base` 改回 `https://<用户名>.github.io/<仓库>/` 就回到原样。

### 日常更新

课表有变动时（建议先用 `diff` 确认）：

```bash
python -m xjtu_calendar fetch --semester 2026-fall
python -m xjtu_calendar subscribe push --semester 2026-fall
```

- push 与 `export` 共用同一条构建管线，但只暴露两个数据源参数：
  `--input`（可直接指定课表 JSON，默认用 fetch 缓存）与 `--semester`。
- 内容与上次发布完全一致时，工具会尽量跳过推送；即便重复推送，效果也是
  幂等的——远端始终只有一个提交，课表没变就不会产生新的变化。
- raw 快照超过 7 天会警告「建议先 fetch」，但不阻断。
- SEQUENCE 基线来自本地留底 `subscribe/last-<学期>.ics`：未变动的事件在客户端
  保持安静，变动的事件原地更新——与重新导入的行为同一口径。
- **本地四样落后于「最后一次真正发出去的版本」时，push 会拒绝并让你先跑 `repair`**
  （0.8.5 起，退出码 7）。四样 = 留底 `last-<学期>.ics`、课程台账 `last-courses-<学期>.ics`、
  考试台账 `last-exams-<学期>.ics`、状态文件里的 UID 配方标记。为什么必须拦：
  一次发布会同时推进远端 ICS 与这四样，它们**不在一个原子域里**——程序死在中途就会留下
  "远端与状态都是新版、留底/台账还是旧版"，而留底正是下次构建的 SEQUENCE 与撤销判定基线。
  两种真实后果（2026-10-14 外部审查补验、均有回归用例钉住）：留底落后 + 课表又变了 ⇒
  产物的版本号从起点就错；留底新而课程台账旧 ⇒ 退课那条 UID 根本进不了候选集，
  **撤销静默漏发**。被拦住时本地一个字节都不会动，远端也不动。
- `subscribe status` 汇总 URL、上次发布时间、本地留底与上次发布记录是否一致、快照年龄；
  `doctor` 的「订阅」项跑的是与 `subscribe push` **同一条**判定（`check_local_compatibility`），
  外加一条**不依赖重建产物**的直比（留底 sha vs 最后一次发布的字节 sha）——
  门会拦的事体检不会看不见，课表恰好也变了的时候同样能看见这个状态。
  **看不见之外还要说重话**（2026-10-15 口径）：这条判定不通过时 `doctor` 判**阻塞项**，
  退出码 `5`，因为"等下次 push 才发现"等于把用户留在错误的基线上多走一次；
  而 `push` 用业务错误 `7`，两个退出码各管各的命令，不必相同。

### 恢复：`subscribe repair`

一次发布要同时推进五样东西（远端 `.ics`、状态文件里的上次发布记录、本地留底、两份台账、
迁移标记），它们不在一个原子域里，所以工具用**两份**私有「发布恢复快照」记账，都在
`subscribe/` 下、发布工作目录**之外**，永不发布、与两份台账同一隐私等级：

- `publish-pending-<学期>.json` —— **这次准备发**的完整目标状态（ICS 字节、两份台账应当
  是什么、不该动的那份台账当时的字节指纹、UID 配方标记）。推送之前写。
- `publish-journal-<学期>.json` —— **已发布凭据**：唯一能代表"远端收下过哪一版"的本地依据。
  只在远端确认收下之后由准备稿提升而来。

有了它们，恢复就不必从公开产物里反推（产物里课程事件与考试事件长得一样，反推不出来）：

```bash
python -m xjtu_calendar subscribe repair --semester 2026-fall
```

`repair` 先从发布分支拉回**线上真实字节**，再在两份凭据之间裁决，**不重新构建、不动
SEQUENCE、绝不产生新的发布**：

- 线上 == 准备稿 ⇒ 那一版其实发出去了（死在登记之前），提升为已发布凭据并按它补回本地。
- 线上 == 已发布凭据 ⇒ 本地那份准备稿从未落地，丢弃它（会说一声，不会静默动你的文件）。
- 两者都不是 ⇒ 中断点不在本地，拒绝自动操作，让你先 `subscribe status` 核对。

顺带把状态文件里的「上次发布记录」也修对（只补文件不修元数据，`status`/`doctor` 会一直报
错误的版本），并在收尾用**同一条判定**复核一遍：可以重复执行，已经完全一致时报「无需恢复」。

四个边界：

- **上一次发布的结果还没裁决**（`publish-pending-<学期>.json` 还在）：这一格 `push` 也拒绝
  （退出码 7）、`doctor` 判**阻塞**（退出码 5）。理由不是"有个文件没删"，而是此刻本地
  四样与**已发布凭据**可以逐样自洽、而线上其实已经是准备稿那一版——这种"自洽地错"正好是
  下一次构建的基线错误，只有 `repair` 手里的线上真实字节能裁决它。裁决完再 push 就是普通一次发布。
- **从 0.8.5 之前升级上来（没有凭据）**：只要留底字节与「最后一次发布记录」逐字节相符，
  push **自动放行**，并打一条警告说清这次没能校验两份台账与迁移标记；推送前会照旧落一份
  凭据，依据就此补回，下一次起就是完整判定。**升级当天不需要加任何参数。**
  `doctor` 对这一格也只给**警告**（放行的是门，体检不能比门更凶）。
  只有连留底也对不上时才会拒绝（退出码 7），此时本地没有依据可查，`repair` 也无能为力，
  人工出口二选一：从订阅 URL 把当前 `.ics` 下载下来原样放回留底路径；或确认可以接受
  全新订阅时删除状态文件重新 `subscribe init`（会清空客户端历史）。
- **凭据读不懂**（被截断、被改坏）与**从没写过**不是一回事：前者说明本该信任的凭据失效了，
  工具不会退回更宽松的判据继续发布，而是拒绝。「读不懂」也包括**自相矛盾**：正文与它自己
  记的哈希对不上、或台账那两项解不出合法文本，都算这一格（宁可停手，也不照着一份坏凭据
  把本地文件改一遍——那会造出"既不等于线上、也不等于任何凭据"的第四种状态）。
- **快照的 token 与当前订阅不符**（别的订阅残留的快照）同样拒绝，绝不拿另一份订阅的字节当依据。
  快照记的**字节哈希**或**发布分支**与状态里的「上次发布记录」对不上时也是同一处理。

还有一格 `repair` 补不回来，会如实告诉你：`--no-exams` 那类"这次不该动考试台账"的发布，
凭据里只留了那份台账**当时的指纹**、没留内容。它要是被删了（或者反过来——当时没有、
后来凭空多出一份），工具不会凭空造一份给你，而是报「仍有本地状态无法恢复」——
从备份或仓库历史找回原文件，或确认可以接受丢掉这段撤销历史时带 `--allow-unverified-baseline`。

急着发、且确认远端就是状态里记的那一版时，`subscribe push --allow-unverified-baseline`
是一个**一次性**出口：它警告后继续，并把凭据重新落下来，下一次就恢复正常判据。
**它管不到两格**——「上一次发布的结果还没裁决」与「凭据读不懂」。这两格的唯一出路是
`subscribe repair`（前者要它拿线上真实字节裁决，后者要你先修好那份文件）：强行继续会把
那份待裁决的准备稿原地覆盖掉，此后谁也无法判断线上究竟是哪一版。
`subscribe rotate` 接同一个旗标，含义与边界完全相同。

### 换 token（rotate）

把 URL 转发给了不该给的人、换了课表环境、或有任何泄露疑虑时：

```bash
python -m xjtu_calendar subscribe rotate --semester 2026-fall
```

换新 token 后 rotate 会顺手重新发布（若之前从未 push 过，则提示你跑
`subscribe push`）。新文件挂上分支、旧文件名从 tip 消失，**旧 URL 自此 404**；
**所有日历客户端都要重新粘贴新 URL**——这是换 token 的固有成本。
rotate 也会把**新** token 的 `webcal://` 链接打印出来（旧的那条随之作废，见下一节），
重订时用新的一条。
补发走的正是 `subscribe push` 那一条发布事务：换 token **之前**先过同一道相容性检查
（不相容就停手，此时 token 还没换、旧 URL 依旧好用），推送之前先落准备稿，成功后才把
凭据与本地的留底/台账对齐。所以 rotate 同样接 `--allow-unverified-baseline`，同样有那两格
它管不到的情况。
极端情况 rotate 后发布失败（网络/权限）：token 已换、远端还挂着旧文件名，
**补发成功前旧 URL 仍可读取**——这正是需要尽快补发（或清理）的原因；
按终端提示修复后跑 `subscribe push` 补发即可。
如果失败发生在推送**之后**（远端可能已经挂上新文件名，只是本地没落盘），提示会改指
`subscribe repair`：先让它拿线上真实字节判定这一版发出去了没有，再决定下一步。

### iOS / macOS：`webcal://` 订阅链接

`subscribe init`、`subscribe push`（含「无变化，跳过推送」那一支）、`subscribe rotate`、
`subscribe status` 四处都会额外打印一行，文案逐字如下：

```
iOS/macOS：通常可直接打开 webcal://<你的 Pages 前缀>/<token>.ics 完成订阅（真机未验证，失败就走 README 的手动路径）。
```

三点缺一不可：

1. **它不是一个新文件**。这条链接只是把同一行里那条订阅 URL 的 `https://` 换成 `webcal://`
   （`webcal` 是 URL scheme，不是文件格式），指向的还是**同一份** `<token>.ics`；发布分支的
   tip 上始终只有那一个 `.ics`。当初考虑过「在 `.ics` 旁边再写一个 `<token>.webcal`」，
   因为会撞 `subscribe` 的 tree 护栏（根目录恰好一个 `*.ics`）与 rotate 只清 `*.ics`
   的清理逻辑而否决，理由见 `docs/design/2026-10-11-subscription-followups.md` §3。
   另外只有 `url_base` 是 **https** 时才打印这一行：非 https 的订阅地址（明文 `http`、
   自建托管给的 `file://` 一类彩排远端）会整行省略——宁可不提示，也不给一条看起来能点
   其实无效的链接。
2. **「点开就弹订阅确认」本项目没有做过真机验证**。这一句按 AGENTS 红线 3 停在「通常」：
   iOS/Safari 拿到 `webcal://` 之后的处置、弹不弹订阅确认，都没有 iPhone 实测读数。
   点了没反应或没能订阅，就走手动路径，两条都能建立订阅：
   - **iOS**：设置 → 日历 → 账户 → 添加账户 → 其他 → 添加已订阅的日历，
     粘贴那条 `https://` 订阅 URL（新版 iOS 把「日历」设置项收进 App 分组，菜单名随系统版本有出入）。
   - **macOS**：日历 App → 文件 → 新建订阅日历（旧版本为「文件 → 添加日历 → 订阅」），
     粘贴 URL，并把「自动刷新」设为一个周期。

   这两条菜单路径同样**未在本项目真机验证**，写出来是 Apple 一贯的入口形态，不是实测步骤。
3. **rotate 之后旧链接随之作废**。换 token 换的就是 URL 本身：补发成功后旧 `<token>.ics`
   从分支 tip 消失，旧 `webcal://` 链接和旧 `https://` URL 一起失效（补发成功前旧 URL
   仍可读取，见上一节），iOS 侧必须用 rotate 打印的**新**那条重新订阅一次。

### 隐私口径

1. **URL 即能力**：token 是 32 位十六进制随机串，猜不到；但知道完整 URL 的
   人就能匿名读取你的课表——**转发 URL 等于授权**。
2. **走路径 A 时，「知道 URL 才能读」这层保护并不成立**：路径 A 的发布仓库必须是公开的
   （GitHub Pages 对免费账户的私有仓库不提供托管），而仓库的分支文件列表页匿名可读，
   会**直接列出** `<token>.ics` 的文件名。也就是说不用猜 token——任何会浏览该仓库
   分支的人都能拿到你的课表，token 实际挡住的是「不知道有这个仓库 / 分支」这一层。
   要把这层保护变成真的，走上面**路径 B**（私有仓 + Cloudflare Pages），
   代价是订阅地址的可达性交给 Cloudflare 的国内路由决定；
   两条路都不接受就退回「导出文件 + 手工导入」，或把导出文件放进你自己的网盘同步目录、
   手机上用 ICSx⁵ 订阅**本地** .ics（零公网暴露）。
3. **产物里有什么，就是公开什么**：默认并进的考试事件会把考试名称、考试时间、考场，
   以及 `DESCRIPTION` 里的座位号一起放进那份匿名可读的文件。不愿意公开就带
   `--no-exams`（`fetch` / `export` / `subscribe push` / `subscribe rotate` 四处都认）。
4. **历史零残留**：发布分支永远是「无父孤儿单提交 + 强推」，课表的旧版本
   不进 git 历史，仓库里翻不到你上周的课表。
5. **部署生效延迟数分钟**（两条托管路都有）：push 成功 ≠ 订阅 URL 立刻是新内容；
   客户端要等 Pages / Cloudflare 部署完成后的下一次自动拉取才呈现新状态。
   `status --verify` 可确认。
   `rotate` 之后这个窗口尤其明显：git 层此刻已经只剩新文件名（旧文件已从
   分支 tip 消失），但 Pages/CDN 可能仍有 1~2 分钟继续供着旧内容——这期间
   旧 URL 还读得到属正常现象，稍后重查即可，不要据此判定 rotate 失败。

token 状态文件按收紧的文件权限写盘（与 `storage_state.json` 同等待遇）；
日志**不落订阅 URL / token**。

### 已知边界

- **课程改名（v0.8.0 起）通常会走原地更新**：课程 UID 改用配方 v2、课程名不再参与身份，
  同一 `course_id` 的课被改名会作为同一事件的新版本被客户端原地覆盖，`diff` 仍会在 push
  之前先把这条时段变化列出来。唯一例外是 `course_id` 缺失、退回用课程名做标识的行——那种行
  改名仍会产生新事件。真退课、教学班换 `course_id` 会以 `STATUS:CANCELLED` 下发，客户端表现
  与考试侧同（Google 网页版会移除；Outlook.com / ColorOS 会留一条「已取消的活动」占位，直到它
  原定时刻过去、从产物退场——而退场之后 ColorOS 仍然不清；整学期规模的迁移残条已在 2026-10-12
  真机演练，见下一节）。
- **换 token 后所有客户端要重贴 URL**（见上）。
- **取消事件在部分客户端不会消失**：会回源的订阅客户端里，Google 日历实测会移除
  `STATUS:CANCELLED` 条目；而 Outlook.com 与 ColorOS 系统日历实测**忽略该字段**，
  把撤销条目当普通事件导入。它们显示的是一条标题固定为**「已取消的活动」**的日程
  （v0.6.1 起；此前是不带标题的「无主题」残条），至少一眼能认出是废弃条目，
  但**不会自动消失**：要等它的原定时刻过去、条目从产物退场，之后 Google 与 ICSx⁵ 会清掉、
  ColorOS 永久留着、Outlook 从未取得读数（分通路判据见下面的行为矩阵）。
  Google 那一格还有更省事的一面：**即使不发墓碑、条目直接从产物里消失，Google 也会把它移除**
  （2026-10-13 试验田实测 ⇒ 它的清理由 UID 缺席驱动，`STATUS:CANCELLED` 不是触发条件）；
  ICSx⁵ 也是按 UID 缺席清理（每次成功同步末尾无条件 prune，2026-10-19 真机读到退场项确实被清掉）；
  不清的只有 ColorOS 那一类。
- **校历事件的删除是有成本的，而且反悔不是无损的**（0.9.0 起，`--include-calendar-events`）：
  校历事件**不接撤销通路**（那是课程与考试两套已冻结的机制），所以把学期配置 `events` 里的条目
  删掉再发布，效果就是"从 feed 消失"——三件事必须说清：
  ①**删除后再加回来，不等于撤销了那次删除**：那一次产物里没有这条 UID、本地留底里的这条身份
  也随之消失，重新加回来时它按**新增事件**发布，`SEQUENCE` 从 `0` 重算（2026-10-15 离线彩排实测：
  产物逐字节退回"从未启用"那一份，再加回来又逐字节等于第一次启用的那一版）；
  ②同一 UID 以更低 `SEQUENCE` 再出现时，客户端**通常**不会接受这次更新（它会认为手里的更新），
  真机未针对校历事件验证过这一条 —— 也就是说旧内容可能一直留在那儿；
  ③`subscribe repair` **修不了客户端已经持有的历史状态**：它只把本地的留底与两份台账对齐到
  线上那一版字节，不发任何新内容，也不碰你手机上那条日程。
  正因为这三条，`subscribe push` / `subscribe rotate` 有一道防误删的门：**上一版发布过校历事件
  而本次没带 `--include-calendar-events` ⇒ 整体拒绝发布（退出码 `8`）**，而不是把你的校历事件
  悄悄清空。确实不想要了就明说——把 `events` 条目删掉（那是明确选择，门放行）。
- **「导入」与「订阅」是两种功能，别混**：导入型入口把 .ics 里的事件一次性写进本机，
  此后不再回源，`subscribe push` 对它无效；订阅型入口才会定期回源。ColorOS 系统日历
  两者都有（「URL 日历」是订阅，「导入日历」是快照）；Google 日历只有网页版能订阅，
  手机 App 里连订阅入口都没有。分辨方法：订阅型入口带「上次同步时间」，导入型只有显示开关。
- 发布通道只有静态 URL（GitHub Pages 或 Cloudflare Pages，见上面「先选一条托管路」）；
  不做 CalDAV 直写、
  不做中心托管服务。

> ⚠️ `~/.xjtu-timetable-calendar/subscribe/work-<学期>/` 是**工具专用**的 git
> 工作区：手工放进去的文件会被下一次 `subscribe push` 原样发布出去
> （记住仓库是公开的！），此后分支 tip 不再满足「根目录仅一个 .ics」的
> tree 护栏，后续发布被 fail-closed 拒绝，直到你清空该目录并自行清空
> （或换名重建）那个分支。**不要往这个目录放任何东西。**

### 升级到 v0.8（UID 配方变更）

v0.8.0 把课程 UID 的配方从 v1 换成 v2（去掉课程名），这是**每个已发布过课表的老用户都会遇到的
一次身份切换**。分客户端说清楚会发生什么：

- **URL 订阅（`subscribe push`）：自动迁移，用户零操作。** 工具靠订阅状态文件
  `subscribe/subscribe-<学期>.json` 里的 `uid_recipe` 字段判断「上次发布用的还是 v1」，
  下一次 `subscribe push` 会自动走一遍迁移：发布前打印一行预告（撤销 N 条 + 原因），
  把整学期旧 UID 标成 `STATUS:CANCELLED` 一次性下发，同时用 v2 重建 live 事件。
  **迁移只在 `subscribe push` 上发生，`export` 永不触发**；发布没成功就不会写任何状态，
  下次 push 仍会重试迁移。

- **迁移跑完之后，同一份课表的下次 `subscribe push` 不会再被门 2 拦。** 课程侧比例熔断只数
  **本次新撤销**——迁移（或往后退课）随产物带出去的那批「已取消的活动」墓碑会在本地课程台账里继续
  被携带，但不会被重复算成新撤销。课表没变时实测输出 `无变化，跳过推送。`、退出码 `0`。

- **手工 `export` 导入者：删除旧日历、重新导入一次。** 迁移撤销不在 `export` 下发
  （`export` 也不读不写 `uid_recipe`），双击导入的旧日历不会被自动收掉。正确做法是把旧的
  课表日历删掉，用 v0.8 重新 `export` 的 .ics 再导一次；此后改课、改名都会原地更新。

- **忽略 `STATUS:CANCELLED` 的客户端（Outlook.com / ColorOS）会看到一次整学期「已取消的活动」。**
  迁移那一次是几百条量级的全量撤销。2026-10-12 在整学期规模（合成身份字段 + 真实时间骨架）的真机
  演练给出 ColorOS 的实测表现：v1 那条 UID 被**原地改写**成标题「已取消的活动」、`LOCATION` 变空
  （产物里墓碑不带该字段，ColorOS 整体替换字段，与 2026-10-10 既有实测吻合），v2 的新 UID 作为**新
  日程**进来 ⇒ 同一时段 1:1 成对出现，整学期规模 = **96 条新日程 + 75 条占位 + 21 条已过原定时刻的旧条目**。
  **关键更正**：这批占位是产物自身携带的 `STATUS:CANCELLED` 事件，忽略 `STATUS` 的客户端退订重加时会
  **再导入一遍**——实测重加后「已取消的活动」仍在、仍 1:1。所以此前写的「退订再重新添加是唯一确定有效
  的清理手段」这句**是错的**：占位只能等各自**原定时刻过去**、从产物里退场，而 ColorOS 对退场项
  也不清（就是下面那 21 条）；退订重加能清掉的只有
  本地重复项，**清不掉产物带着的占位**。至于那 21 条已过原定时刻的旧条目（被过期筛放掉、不产生墓碑），
  本次是**先删除该日历、再重新添加**，它们**仍在**手机上 ⇒ 对这类"从产物里彻底消失"的条目，
  退订重加同样无效。我们没记录删除时是否勾选了「同时删除事件」，所以不对 ColorOS 的删除语义下断言；
  但作为面向用户的补救手段，「退订重加」在本次演练里**已被证伪**——**ColorOS 原生订阅**上占位靠
  "原定时刻过去、从产物退场"也换不到清理（它没有 prune），而"消失项"连手动删都做不到（2026-10-15
  实测单条删不掉），只剩隐藏那本日历或换 ICSx⁵ 两条路。
  **Google 那条腿的「消失项」这一半已于 2026-10-13 复验**：同一份整学期规模的合成课表、隔离的试验田仓库，
  产物从 96 事件换成 91 事件、抽掉 5 条且**不发墓碑**，Google 网页版**5 条最终全部移除**
  （4 条截至 T+14h39m、最后一条截至 T+24h58m，同批对照条目全程健在）⇒ Google 用户**不会**积累这类
  幽灵条目，它的清理由 UID 缺席驱动。
  仍未复验的是「Google 在整学期规模会不会清掉那批『已取消的活动』占位」（v0.6 只在小规模上验过它认
  `STATUS:CANCELLED`）；按上面这个机制推断它同样会清，但**那句是推断、不是实测**。

- **回滚不是免费的。** v2 事件一旦发布，退回 0.7.x 会重新发一批 v1 UID，订阅端于是出现**双份**事件，
  补救同样只有退订重加。所以真出问题应当**停在 0.8.0 往前修**，而不是去手改状态文件里的 `uid_recipe`
  ——手动改写只会让迁移分支反复触发，解决不了问题。

- **撤销通路还有一道兜底降级。** 当 v2 配方下出现「同课程号 + 同一天 + 同节次、课程名却不同」的 UID
  碰撞时（分层/分项教学班这类形状），工具会放弃本次课程撤销并给出一条只报数量的提示，课表产物与考试侧不受影响。

### 常见客户端订阅入口

- Apple 日历：走**订阅**入口而不是导入（macOS 日历 App「文件 → 新建订阅日历」，
  旧版本为「文件 → 添加日历 → 订阅」；iPhone「设置 → 日历 → 账户 → 添加账户 → 其他 →
  添加已订阅的日历」）。`subscribe` 打印的那行 `webcal://` 链接是给 Apple 用户抄的捷径，
  **未在本项目真机验证**，点了没反应就回上面这两条手动路径
  （完整口径见「iOS / macOS：`webcal://` 订阅链接」）。
- Google Calendar：**订阅只能在网页版建立**——打开 calendar.google.com，左侧「其他日历」
  旁的「添加日历」→「通过 URL 创建 / 从 URL 添加」（各语言版本措辞略有差异）。
  **手机 App 里没有这个入口**；而且实测：网页端建好之后，手机上的 Google 日历 App
  仍然**不显示**这类「从 URL 添加」的日历（勾过 `syncselect`、强制同步、走代理都不行），
  Google App 的「同步」开关只覆盖你自己创建的日历。所以要看手机课表，请走下面的
  系统日历订阅，别把希望放在 Google App 上。
  当前版本的日历设置里**没有**「自动移除旧事件」这一项（旧文档常提到它，已不存在）——
  好消息是它不影响撤销：`STATUS:CANCELLED` 的条目是**在场地**出现在产物里的，
  Google 实测会据此移除日程（见下面的行为矩阵）。
- **Android**：首选 **ICSx⁵**（`at.bitfire.icsdroid`；**免费**获取地址
  <https://f-droid.org/packages/at.bitfire.icsdroid/>），不分 ROM 统一走它。原因不是系统自带入口
  不好用，而是**各家自带入口的能力参差不齐**——MIUI / 鸿蒙常常只给「导入日历」，那是一次性快照、
  永不自动更新；只有它才有订阅语义。ICSx⁵ 专门做 URL / 本地 `.ics` 订阅并把事件写进系统日历数据库。
  **注意不是 DAVx⁵**——DAVx⁵ 只做 CalDAV 双向同步，遇到 Webcal 集合是把 URL 转交给 ICSx⁵，
  自己不拉纯 HTTP 的 `.ics`，按 DAVx⁵ 操作是找不到入口的。
  两条要先交的成本：① **分发**——F-Droid 免费、各应用商店按我方口径收费，直下 APK 要允许未知来源，
  而 `github.com` / `f-droid.org` 在国内网络下实测不可达，下载环节通常要挂代理；② **给同步器关闭
  电池优化并允许自启动**，否则后台查杀会伪装成"装了但不更新"。
  ICSx⁵ 相对系统自带订阅的三点差别（逐条判据与读数见
  `docs/design/2026-10-11-subscription-followups.md` §13）：
  ① 每次成功同步末尾会**无条件清理**源里已不存在的 UID —— **2026-10-19 真机确认在 GitHub Pages
  这条通路上生效**（两条从未手删过、随发布从 feed 消失的占位，同步后界面上都不在了）；
  ② `STATUS:CANCELLED` 不被丢弃，而是映射成系统日历的"已取消"状态落库 —— 于是显不显示变成日历 App
  的问题（2026-10-15 实测：ColorOS 自带日历照旧显示成普通日程，换通路只把问题从同步侧挪到显示侧）；
  ③ 日历是**只读**的，源码上看不出它会不会尊重本地删除 —— **这条推论已被 2026-10-19 的真机读数否证**：
  手删一条仍在产物里、原定时刻在未来的占位，同步之后**没有再出现**。
  ⇒ **ICSx⁵ 上那条「已取消的活动」可以自己删掉，删了不回来**，不必干等原定时刻自然退场。
  两条读数的限制要一并记住：判据是**界面级**（库里那一行是硬删还是打软删除标记，未取）、
  单账户单样本、且**换个订阅器不成立** —— ColorOS 原生订阅仍然手删 / 重加 / 删除订阅三条全部无效。
- **ColorOS 系统日历（ICSx⁵ 装不上时的兜底）**：自带「URL 日历」入口——「日历 → 我的 → 添加日历 →
  **URL 日历**」，粘贴订阅地址即可，实测（2026-10）它会自动回源并**原地更新**已改变的事件，
  日历名直接采用 `X-WR-CALNAME`。不想装第三方 App 就用这条，但要清楚它的三点缺陷：
  忽略 `STATUS:CANCELLED`（撤销条目显示成一条普通日程）、从产物消失的条目**永不删**、
  **单条也删不掉**——2026-10-15 真机确认「删除订阅」同样不带走本地事件。
  已经用过 ColorOS 原生订阅再切到 ICSx⁵ 的，旧那本清不掉，只能在日历列表里**取消勾选（隐藏）**；
  两本的 live UID 完全相同（token 不进产物），跨日历会不会互相干扰尚未验证。
  另有一条通用坑与通路无关：一次性导入产生的独立日历，在日历 App 里常常只有「隐藏」没有「删除」——
  真正的删除入口在 **设置 → 用户与账号 → 账户与同步**，移除导入产生的那个
  账户即可。**不要**用「设置 → 应用 → 日历 → 清除数据」，那会连你自己的
  日程一起清空。

#### 客户端行为矩阵（2026-10 真机演练；单账户单样本，别当厂商承诺）

**ICSx⁵ 那一行是唯一的例外：它的三条语义里有两条已在 2026-10-19 拿到真机读数**，逐格判定见表下说明。

| 客户端 | 订阅入口 | 收到 `STATUS:CANCELLED` | 条目从 feed 静默消失 | 自动回源 | 用 `X-WR-CALNAME` 命名 |
|---|---|---|---|---|---|
| Google 日历（网页） | 其他日历 → 通过 URL 创建 | **移除条目** | **也会移除**（清理由 UID 缺席驱动，墓碑不是触发条件） | 是；两次实测延迟分别 ≤3h31m、≤10h05m | 是 |
| Google 日历（手机 App） | **无此入口** | 不适用——App 不显示 URL 导入型日历 | 不适用 | 不适用 | 不适用 |
| Outlook.com（网页） | 添加日历 → 订阅日历 | **忽略**，当普通事件导入（当时产物无标题 ⇒ 显示「无主题」） | **未验证**（该面回源周期未取得） | 添加时立刻拉一次；此后实测 **14 小时以上未再回源**（官方口径约每 3 小时） | 否，对话框强制手填 |
| ColorOS 系统日历 | 我的 → 添加日历 → URL 日历 | **忽略**，同上；且它是**整体替换字段**，旧标题会被清掉 | **不删**，永久留着（退订重加也清不掉） | 是；实测延迟 ≤2h35m，且能原地更新已存在的事件 | 是 |
| ICSx⁵（Android，第三方订阅器） | 在 ICSx⁵ 里粘贴 URL，事件写进系统日历数据库 | 上游源码把它映射成系统的"已取消"状态落库；**但真机读数：ColorOS 自带日历照旧显示成普通日程**（2026-10-15）⇒ 换了通路只是把问题从同步侧挪到显示侧，观感没变，剩下的是日历 App 过不过滤的问题 | **会删**（2026-10-19 真机确认：两条从未手删过、随发布从 feed 消失的占位，同步后界面上都不在了；控制证据是同批发布新增的校历事件已在手机上出现 ⇒ 那次同步拿到的是全文，不是 `304`） | 是；回源间隔由 ICSx⁵ 自己的设置决定，**默认值未核实**；国产 ROM 要关电池优化并允许自启动 | **是**（2026-10-15 真机：自动就是课表名，没让填） |
| 各类「导入日历」 | 选本地 .ics 文件 | 不适用（不再回源） | 不适用 | **否**，一次性快照 | 不适用 |

ICSx⁵ 这一行的证据强度仍然**不是齐平的**，别整行当实测读：入口、日历名、取消条目"照旧显示成普通日程"
是 2026-10-15 在**正式订阅**上的真机读数（单账户单样本）；"`STATUS` 映射成系统 canceled 状态落库"
仍是**上游源码取证**——真机只看得到显示层，看不到库里那个字段。
**2026-10-19 补上两格**：① "消失项会被清理"真机成立；② **单条删得掉、且同步后不回来**。
先前据源码（只读日历 + 无"用户删过"记录）判定删不动，而 10-15 那次"能删但没回来"因为缺对照
（被删那条的原定时刻可能已经过了，那是产物退场 + 清理共同作用）只能记"未定"。
这次是在**发布之后**看的，并且用同批新增的校历事件证明那次同步拿到的是全文而非 `304`，
被删那条的原定时刻还在两个多月之外 ⇒ 对照成立，源码那条推论**被否证**。
⇒ 对 ICSx⁵ 用户可以直接说**占位自己删得掉**。两点限制要跟着说清：判据是**界面级**
（库里那一行是硬删还是打软删除标记，本项目未取），而且这条**只属于 ICSx⁵**——
ColorOS 原生订阅上手删 / 退订重加 / 删除订阅三条全部无效。
判据与探针协议见 `docs/design/2026-10-11-subscription-followups.md` §13。

「条目从 feed 静默消失」这一列是 2026-10-13 在**试验田仓库**（不是正式订阅）上单独测出来的：
一份 96 事件的整学期规模产物换成 91 事件，抽掉 5 条**不发墓碑**、其余字节与 URL 都不动。
Google 网页版**截至 T+14h39m 已移除其中 4 条**，同批 7 处对照条目全部健在（⇒ 不是"没回源"）；
最后一条（当时距今 58 天的 12-10）在 **T+24h58m 的周视图复核里也已消失** ⇒ **5 条全清、对照全在**。
ColorOS 那一格沿用 2026-10-12 整学期迁移演练的读数（21 条被过期筛放掉的旧条目，删除日历再重新添加后
**仍在**手机上）；Outlook 从来没拿到过这个读数，照实写未验证。
读这个数必须用**周视图**：Google 的月视图单元格会静默裁切溢出条目（不给「另外 N 项」），
而且缓存滞后于服务端状态——本次首读就被它骗过一次。

表里「无主题」那一格记的是**演练当时**的读数，当时的撤销条目刻意不带标题。v0.6.1 起
产物给撤销条目带上固定标题「已取消的活动」，客户端"忽略取消字段"这一判定不变，
但残条从「无主题」变成一条写着该文案的日程——认不出来 vs 一眼看穿，差别就在这里。
ColorOS 的「整体替换字段」正是这条改动能在手机端直接生效的前提（10-11 真机读数）。

两点必须如实了解：① 撤销通路目前只在 **Google 网页版**上验证为端到端可用；② 订阅型日历
在 Google 侧是**只读**的——没有"删除单条事件"的入口。而那条「已取消的活动」占位是**产物自身
携带**的 `STATUS:CANCELLED` 事件，忽略该字段的客户端**退订重加时会再导入一遍**（2026-10-12 真机
实测：重加后占位仍在、仍与新日程 1:1）。所以退订重加**清不掉占位**，只能清掉本地重复项；占位要等
各自原定时刻过去、从产物里退场。Outlook 的删除入口仍未验；**ColorOS 那一格已确认（2026-10-15
正式订阅真机）：那条占位单条删不掉，而移除订阅只有「删除订阅」一个动作、不带走本地事件**——与
10-12「删除日历再重新添加后 21 条仍在」互相印证。⇒ 在 **ColorOS 原生订阅**这条通路上没有任何可用的
清理动作，连"等它到点退场"都换不到清理，剩下的唯一杠杆是改写那条条目而不是删除它，见
`docs/design/2026-10-11-subscription-followups.md` §12。**这个结论不通用于 Android**：ICSx⁵ 每次
成功同步末尾都会清理源里已不存在的 UID（上游源码取证，**2026-10-19 真机读到它确实清掉了两条退场占位**），
也尊重用户手删（同日实测：手删的占位同步之后没有再加回来）⇒ 换通路之后「从产物里摘掉」第一次
等于「手机上被删掉」，判据与限制见同文 §13 第 12 点。
