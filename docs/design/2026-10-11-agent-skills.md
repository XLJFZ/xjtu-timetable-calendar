## 1. 为什么要做成 skill，而不是再写一份文档

README 已经服务"人"了。它服务不了的是**agent 替人执行时的判据**。这套流程里最容易让
agent 出错的地方，全都属于"文档写了但 agent 会做错"那一类：

- 登录是交互式的（终端要真人按 Enter）。agent 把它放进后台任务或管道，就永远等不到那个
  回车，表现成"卡住"，还会留一个占住 profile 目录的浏览器窗口。
- "用户说他已经登录了 eHall"是**无效证据**：工具用的是独立浏览器实例，平时浏览器里的
  登录态对它毫无作用。判据只有两条——会话文件的修改时间变了、`fetch` 不再 401。
- 校历与作息表**必须问用户**，工具刻意不内置猜测值。agent 的本能是"从数据里推"，那会
  把学期起始日猜错，于是整学期周次全错，而产物看起来完全正常。
- 客户端怎么处理撤销、多久回源一次，是**实测事实**，猜不出来，而且猜错的建议会让用户
  白等一天。

skill 的价值就是把这四类东西变成**带证据的检查点**，而不是散在长文档里的提醒。

## 2. 交付形态

两个 skill，源码放在仓库根的 `skills/` 下，与 CLI 同仓库同版本：

```
skills/
  xjtu-timetable-setup/          # 部署向导（有承诺：能走到"手机上看到课表"）
    SKILL.md
    scripts/check_setup.py       # 确定性体检，输出给 agent 读
    references/troubleshooting.md
    references/client-matrix.md  # 见 §5 的权威关系
  timetable-source-onboarding/   # 接口考古方法论（不承诺接入成功）
    SKILL.md
    references/probe-checklist.md
    references/red-lines.md
```

**安装**：把 `skills/<name>/` 整个目录复制进使用者所用 Agent 的 skills 目录
（项目级与用户级均可，不同产品的目录名不同，以对方文档为准）。本文**不写死某个
Agent 产品的路径与名称**——既是仓库既有的隐私红线（跟踪内容不出现工具品牌名），
也因为这个格式事实上是通用的。

**版本偏斜**是这套形态的固有代价：skill 随仓库走，CLI 随 PyPI 走，两者版本会不一致。
处理方式是**让 skill 自己去查**，而不是靠"请保持版本一致"这种祈使句：
`SKILL.md` 第一步就要求跑 `xjtu-calendar --version` 与 `check_setup.py`，
并在文中显式写出"本文按 0.6.1 的行为编写；若检测到的版本低于此，某些判据不适用"。

## 3. Skill 1：`xjtu-timetable-setup`（部署向导）

**自由度定级：低。** 顺序脆弱、错了会静默产出坏日历，所以每一步都给具体命令与
**可验证的证据**，agent 不许在拿不出证据时宣布成功。

八步骨架（每步格式：动作 → 证据 → 不满足时怎么办）：

1. **环境** — `python -c "import xjtu_calendar"` + `--version`。证据：版本号 ≥ 本文标注版本。
2. **登录** — **把命令原样交给用户，让他在自己的前台终端里跑**；agent 只回收证据
   （会话文件 mtime、`fetch` 不再 401）。这一步是"高自由度禁令"：明确写出禁止后台执行、
   禁止管道、禁止替用户按回车。
3. **校历** — 只问三件事：学期起始日、周次总数、本学期标识。**禁止推断**。证据：
   配置校验通过、`export` 不报校历缺失。
4. **作息表** — 优先用 `schedule` 子命令抓官方页（切换点取自页面原文）；抓不到就问用户。
   证据：钟点表非空且通过校验。
5. **`fetch`** — 证据：快照落盘、事件数 > 0、解析报告里 skipped 条目已逐条读过。
6. **`export`** — 证据：`.ics` 里 VEVENT 数与事件数吻合；重复导出 UID 不变（这是订阅通道
   能原地更新的前提，值得让 agent 亲手验一次）。
7. **订阅发布** — 需要用户自己的仓库与静态托管。skill 在这里要如实说出两件事：
   token 等价凭据；**若发布仓库是公开的，分支列表能直接翻到 `<token>.ics` 的文件名**
   （实测事实，不是理论风险）。证据：`subscribe status` 显示留底一致，且线上 URL 返回 200。
8. **选客户端** — 按矩阵给建议，并说明为什么：一次性导入不回源、部分客户端忽略取消字段、
   各家回源周期都是小时级且不可强制刷新。

`scripts/check_setup.py` 承担"agent 每次都要重写一遍的那段代码"：一条命令跑完
版本 / 会话新鲜度 / 快照年龄 / 产物事件数 / URL 可达性，输出紧凑的成功失败清单
（不打 traceback，不打印任何个人信息）。它把第 5–7 步的证据收集从"agent 自由发挥"
降级成确定性动作。

## 4. Skill 2：`timetable-source-onboarding`（接口考古方法论）

**自由度定级：高。** 面对的是未知的系统，能给的只有启发式与停止条件。
开头一句边界声明：**本 skill 不产出能用的订阅**，它承诺的是"别把已知的坑重新踩一遍"。

内容按可执行判据组织，而不是按道理组织：

- **第 0 步是合规与授权**：目标学校的条款是否允许程序化访问？问不清就停，并把"我停在哪"
  写清楚。凭据永远由用户本人输入，agent 不代填、不读取、不保存。
- **观测四问**（每一问都要 payload 里的证据）：字段与语义键能否一一对上；周次是位掩码、
  文本还是日期区间；学期怎么发现、代码格式是什么；**"没有数据"与"查询失败"能否区分**。
- **第四问是 go/no-go**，不是打分项：区分不了，撤销通路在该系统上就是**不可用**而不是稍差
  ——因为"空"既可能是真的没有，也可能是抓取失败，任何一侧误判都会撤销用户已发布的整学期。
- **身份字段决定表现**：选错会让"改期"变成"删了重建"，客户端里旧事件永远留着。
- **对照探针原则**：每个待判信号必须配一个必然可见的变化，否则"什么都没变"无法解释。
  这条是我们花了一整晚演练才换来的。
- **安全停止条件**清单：什么时候该对用户说"这所学校需要单独评估"。

## 5. 单一权威：矩阵这类实测事实放哪

客户端行为矩阵的**权威版本在 README**（它带实测日期与设备限定）。skill 里那份
`references/client-matrix.md` 只保留"怎么用这条事实做决策"，并在文件头写死一行
同步标记：`来源：README 客户端行为矩阵，同步于 <把当时实际的 commit 短 sha 填进来>`。
**每次改动 README 矩阵，必须同时更新这个 sha**——没有同步标记的副本就是漂移的起点。

理由很实际：今晚我们花了力气清掉的就是"两处说法不一致"（Google 那个不存在的开关、
DAVx⁵/ICSx⁵ 写反）。skill 与 README 分家之后一定会漂移，所以要么只留一份，
要么在 skill 里显式钉住同步点。本文选后者，因为 agent 需要就近读到判据。

## 6. 格式符合性

按现行 skill 规范执行：`SKILL.md` 的 frontmatter 必须有 `name`（小写连字符，
与目录名一致）与单行 `description`（≤1024 字符，同时说清"做什么"和"什么时候用"）；
正文用祈使句、控制在 500 行以内，细节下沉 `references/`；只建真正需要的资源目录，
**不在 skill 目录里放 README/CHANGELOG 这类附属文档**。

仓库门禁方面要注意：`ruff format --check .` 会格式化 Markdown 里的 ```python 代码围栏，
所以 skill 文档里的示例一律用 `bash` 或 `text` 围栏。

## 7. 验收：能验什么，不能验什么

- **能验**：`check_setup.py` 必须真跑通（它属于"必须实测的脚本"）；两个 skill 过一遍
  格式自检清单；在一个**已装好**的环境上走一遍第 1–8 步，确认每一步的证据确实取得到。
- **不能验**：**新用户旅程**。我这台机器环境是热的——登录已完成、校历与作息已配好、
  订阅已发布，所以"从零开始的人会不会卡住"验证不到。这一条必须写进 skill 文档的
  已知边界，而不是靠"步骤看起来对"糊过去。真要验，得找一个没装过的同学或干净环境。
- 第二个 skill 的判据（三态可区分性、身份字段）在西交大这一家身上是**有实证的**；
  在别的系统上是否成立，取决于使用者带回来的观测——这是它设计上就承认的局限。

## 8. 站点更新（另案，bounded）

与 skill 无关，但同一批用户会先看站点。`index.html`（275 行手写单页，随 main 构建）
实测内容停在 v0.4 之前：考试 **0 次**、撤销与 `STATUS:CANCELLED` **0 次**、ColorOS **0 次**、
ICSx⁵ **0 次**、年级后缀 **0 次**，`subscribe` 只在"三步上手"里出现一句。
要补的是：考试安排、撤销通路（含"部分客户端不会消失、会留一条写着『已取消的活动』的日程"）、
手机侧到底订哪个客户端，并把"三步拿到第一份日历"扩成含订阅的那条路。
保持手写风格，不引入构建工具。

## 9. Non-goals

- 不做"自动接入任意学校"的能力（第 4 节是方法论，不是爬虫）。
- 不把 skill 发布到任何市场或独立仓库；先随代码走。
- 不在 skill 里内置任何真实姓名、学号、路径、订阅 token。
- 不改 CLI 的行为来迁就 skill（如果 skill 写不下去，那是 CLI 的接口问题，另立议题）。

## 10. 需要拍板的三件事

1. `skills/` 放仓库根，还是放 `.agents/skills/` 之类更"约定俗成"的位置？（本文按仓库根写）
2. `check_setup.py` 要不要同时作为 CLI 子命令发布（例如 `xjtu-calendar doctor`）？
   放进 skill 只帮到 agent 用户，做成子命令则所有人都能用，但要过版本发布流程。
3. 第二个 skill 的名字：`timetable-source-onboarding` 还是更直白的
   `timetable-api-archaeology`？命名会出现在别人 Agent 的技能列表里。
