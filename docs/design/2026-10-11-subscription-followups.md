## 0. 一条先行的判断：别再优化产物格式

演练过程中把产物的结构兼容性实测了一遍：`VTIMEZONE` 块、`X-WR-TIMEZONE`、统一 CRLF、
长行折叠**都在**，三家客户端（Google / Outlook / ColorOS）都能正确解析时间与中文。
两个已知小瑕疵都不值得动：

- 最长行 76 字节（RFC 5545 建议 ≤75，实测三家全接受，且由第三方库折叠，改它等于跟库较劲）；
- 内嵌的 Asia/Shanghai 时区定义带「只适用于 1970–2038」的注释（我们的事件永远在一学期内）。

**泛用性的瓶颈全部在客户端语义层**，不在编码层。下面几条都是语义/分发/操作层的议题。

## 1. 撤销条目的固定标题（v0.6.1 候选，成本最低）—— **已落地（2026-10-11）**

**落地形态**：`exams.CANCELLATION_SUMMARY = "已取消的活动"`，由 `build_cancellation_events`
赋给每条撤销事件；`render_ics` 那个"空标题不写行"的条件保留，职责退化为纯空值守卫。
规格侧 D3 已就地修订（`2026-10-09-exam-cancellation.md` §2 的 D3 行、§6.2 注、§9 新增用例），
三条新用例钉住：标题恒为该文案、产物不含台账原文、多条撤销标题两两相同（SEQUENCE 不漂移）。
下面原文保留，作为当时的判据记录。

**现状证据**：撤销条目按 D3 刻意不含 `SUMMARY`。认 `STATUS:CANCELLED` 的客户端（Google）
会直接移除，无影响；**不认的客户端（Outlook.com、ColorOS，均实测）把它当普通事件导入**，
于是留下一条**没有标题**的日程——用户既认不出它是废弃条目，也不知道该不该删。

**改动面**：`exporter.py` 的撤销分支给一个**不含任何个人信息**的固定标题（例如
「已取消的活动」）。隐私代价为零：不新增姓名/考场/座位/课程名。
D8 的序号幂等不破：标题每次渲染都相同 ⇒ `event_fingerprint` 输入不变 ⇒ 序号不漂移。

**前置条件 —— 已满足（2026-10-11 15:3x 真机读数）**：ColorOS 对已存在事件做的是
**整体替换字段**，不是逐字段合并：演练最后一步把已经带标题显示过的丁转成撤销条目
（同一 UID、`SEQUENCE` 递增、新版本不含 `SUMMARY`）后，手机上那条日程**变成了「无主题」
但没有消失**（旧标题被清掉了）。⇒ 加了固定标题之后，**手机上的取消过程会自动变成一条
写着「已取消的活动」的日程**，用户零操作。这一项因此从"待验证"升级为"可直接排期"。
（Outlook.com 侧的同一转换尚未观测到——它 14 小时以上没有回源，不能替它下结论。）

**要同步改的**：`docs/design/2026-10-09-exam-cancellation.md` §9 里钉着一条用例
「产物中不得出现 `SUMMARY:` 空值行」——那是 D3 的看守。本改动会把它从"不许有标题行"
改成"标题行只能是那个固定值"，属于**规格变更**，不是让测试变绿的手段。

## 2. 课程撤销通路（**v0.8 候选**，价值最大、风险也最大）

> 版本号注（2026-10-11）：本项原占 0.7.0，因 `doctor` 是新增 CLI 能力而让位到 0.8.0，
> 见 `docs/design/2026-10-11-agent-skills.md` §3.1 的拍板记录。

> **落地形态（v0.8.0，2026-10-12，见 `2026-10-12-course-cancellation-uid-v2.md`）**：本节已实现，
> 但**比这里的原计划多做了一步根治**——原 §2「不做的事」写「不改 UID 配方」，被 CD1 推翻：
> 单纯把考试那套搬到课程上会让改名表现为整学期几百条「已取消的活动」，所以 v0.8 同时把课程 UID
> 换成配方 v2（去掉 `course_name`，改名走原地更新，`course_id` 缺失时仍退回 `name:课程名`，CD16），
> 并在 `subscribe push` 上做一次性 v1→v2 迁移（`export` 不参与，CD3）。上面三条前置条件全部落地：
> 门 1 数据可信（`assess_courses`，CD13）+ 门 2 比例熔断（≥ 10 条且 ≥ 台账 30% 即拒绝发布、
> 退出码 `6`、`--allow-mass-cancellation` 放行，CD12）、课程台账
> `subscribe/last-courses-<学期>.ics`（CD8）、`--from-date/--to-date` 裁剪零影响（过滤前捕获 live 集，CD14）。
> **本项没有搭车的部分**：`.webcal` 分发（下面 §3）明确不在本版——CD19 把它排到 0.8.x 独立一笔。
> 下面原文保留，作为当时的判据记录。

**现状证据**：课程 UID 的配方**包含课程名**（`exporter.py:95` 起写明是 legacy 契约：
自 v0.1.0 就随正式版发布，改它会让已导入用户的整学期被识别成新事件，需要显式迁移方案）。
于是**改课名 / 换任课老师导致课程行身份变化**时，订阅端的表现是「旧事件消失 + 新事件出现」，
而 v0.6 的撤销通路按 D17 **只管考试、不管课程**——旧的那批事件**永远不会被收掉**，
残留的还是带真实课程名的整学期日程。

这个场景在学期中比「考试取消」常见得多，后果也更糟，是目前最大的一个泛用性/正确性洞。

**为什么不能照搬考试那套**：撤销候选 = 台账 UID − 本次 live UID。对课程而言，
"本次没有课程"和"课表没抓到/解析炸了"在现有代码里**返回的都是空集**——正是 spec D18
给考试侧补的那道门槛要防的失败模式，而且课程侧的后果是**撤销整学期课**。

**前置条件（缺一不可）**：

1. 课程侧的可信度门槛，强度不低于 `exams_trusted`：快照来源可信、行数不低于一个下限、
   单次撤销数量占既有事件的比例超过阈值就**拒绝发布**并报错；
2. 课程台账（与 `last-exams-*.ics` 同等待遇：本地私有、全字段、发布成功后才回写）；
3. 明确 `--no-exams` 那类"渲染口径开关"在课程侧的对应物（`--from-date`/`--to-date`
   裁剪会不会被误判成"课程消失了"——D19 的教训在这里更尖锐，因为裁剪是常态操作）。

**不做的事**：不改 UID 配方。UID v2 需要迁移方案，是另一份规格，不该被这个议题顺带夹走。

## 3. `.webcal` 分发 → **改为输出 `webcal://` 链接，不发 `.webcal` 文件**（0.8.x 决定，2026-10-12）—— **已落地（2026-10-12）**

**决定与理由**（原方案是"在 `.ics` 旁边多写一个 `<token>.webcal`"，四条理由否决）：

1. `webcal://` 本来就是 **URL scheme**，不是文件格式——`.webcal` 文件的内容就是一行 webcal URL。
   我们的 `.ics` 已经有稳定 URL，把 scheme 换掉就是同一个地址 ⇒ **不需要任何新文件**。
2. 发布分支的 tree 护栏断言「根目录恰好一个 `*.ics`」（`subscribe.py:279-291`）。多一个
   `<token>.webcal` 会让 `len(listing) == 2` ⇒ **下一次发布被自家护栏判成"分支被污染"而拒绝**；
   要放行就得放宽护栏，而护栏的职责正是"别把用户的工作仓库强推覆盖掉"，为省一个链接去削它不值。
3. `rotate` 会换 token，而清理只 `unlink` `*.ics`（`subscribe.py:297`）⇒ 旧 `<token>.webcal`
   会留在 tip 上，同样撞死护栏。这是原方案里没写到的新 bug 面。
4. 多一个公开文件就多一个可枚举面（本文第 4 条），而且 GitHub Pages **不能设自定义
   `Content-Type`**，`.webcal` 多半以 `application/octet-stream` 下发，在 iOS 上反而不如
   直接点 `webcal://` 链接可靠。

**落地形态（2026-10-12，0.8.x 的第一笔）**：`SubscriptionState` 有了只读属性 `webcal_url`
（`subscription_url` 的 `https://` → `webcal://` scheme 替换；非 https 的 `url_base` ——
明文 `http`、`file://` 彩排远端 —— 返回 `None`），CLI 的 `_print_webcal_hint` 在**四处**各打一行：
`subscribe init`、`subscribe push`（含 `NO_CHANGE` 那一支——幂等跳过往往是用户第二次看到入口）、
`subscribe rotate`（打的是**新** token 的链接，旧链接随之作废）、`subscribe status`。
文案为「iOS/macOS：通常可直接打开 <链接> 完成订阅（真机未验证，失败就走 README 的手动路径）」。
发布分支的 tip 形态**未变**，仍然只有一个 `<token>.ics`（有用例钉住）；README 补了
「iOS / macOS：`webcal://` 订阅链接」一节给出手动路径与三条口径，`skills/` 的第 7 步与
`references/client-matrix.md` 同步，并写明这一改动不产生新发布物，防止下一个 agent 又去发文件。

**红线 3 仍然适用**：「iOS/Safari 点 `webcal://` 会弹订阅确认」是常识但**未在本项目真机验证**，
输出与文档一律写「通常」并注明未验证。iPhone 侧的端到端订阅（点了到底弹不弹、订阅后是否定期回源）
仍是**待做的真机演练**，本轮只落了链接与文案。

### 原方案存档（为什么曾考虑发文件）

**现状**：iOS/macOS 的订阅入口藏在「设置 → 日历 → 账户 → 添加账户 → 其他 →
添加已订阅的日历」，用户要手贴 URL；而 `.webcal` 链接点一下就能完成订阅。

**改动面**：发布时在 `.ics` 旁边多写一个 `<token>.webcal`，内容只有一行
`webcal://…/<token>.ics`。GitHub Pages 托管任意静态文件，不需要额外配置。

**代价与风险**：① 发布分支的 tree 护栏现在断言「根目录恰好一个 `.ics`」，
新增扩展名要确认护栏计数口径不被误伤（它按 `.ics` 后缀过滤，理论上是安全的，但必须实测）；
② 多一个公开文件就多一个可枚举面，见第 4 条；③ README 要加一句 iOS 路径。

## 4. 订阅 token 的公开面（口径问题，不是功能问题）—— **措辞已落地（2026-10-11）**

**落地形态**：README 的两处口径（「URL 订阅 → 隐私口径」与「隐私与安全 → 订阅 URL 的
风险口径」）与站点落地页的隐私节，全部改成诚实版本——暴露面有**两处**：转发 URL 等于授权，
而公开仓库的分支文件列表页匿名可读、会直接列出 `<token>.ics` 的文件名；同时写明
「产物里有什么就是公开什么」（默认并进的考试事件会把考试名、时间、考场与 `DESCRIPTION`
里的座位号放进那份公开产物，`--no-exams` 可关）。仓库根 `skills/` 的第 7 步本来就已经
如实告知这一层，现在三处口径一致。
**没有落地的部分**：本节列出的三个方向**一个都没选**——发布仓库转私有受免费账户限制（见第 7 条）、
换托管暂缓、"接受现状"现在成了默认口径。措辞只是不再高估保护强度，**不等于暴露面被修掉了**。
下面原文保留，作为当时的判据记录。

**现状证据**：发布仓库是**公开**的，`tree/<分支>` 页面匿名可读，会**直接列出**
`<token>.ics` 的文件名。也就是说 README「风险口径」里那句「URL 里的随机 token 猜不到，
但知道 URL 就能读」——它的**第一层保护在公开仓库上并不成立**：不需要猜，浏览分支就能拿到。
token 仍然挡得住"别人不知道有这个仓库/分支"这一层，但挡不住任何会看分支列表的人。

**这不是演练的一部分，也不该由文档悄悄改掉**。可选方向（各自都有代价，需要用户拍）：
发布仓库转私有（GitHub Pages 对私有仓库要付费档）、换非公开分发（网盘 / 本地文件 +
ICSx⁵ 那条零公网暴露的链路）、或者接受现状但把 README 的措辞改成诚实版本
（「任何能浏览该仓库分支的人都能拿到课表」）。

## 5. 客户端行为矩阵的维护方式（流程，不是功能）

README 现在有一张矩阵表（Google 网页 / Google App / Outlook.com / ColorOS / 一次性导入 ×
订阅入口 / 认不认取消 / 自动回源 / 用不用 `X-WR-CALNAME`）。它的问题是一次性：
客户端会改版，厂商口径和实际行为也会分叉（本次就实测到 Outlook 官方"约每 3 小时"
对上 14 小时以上未回源）。

**建议的纪律**：① 表里每一格都要有「实测日期 + 设备/版本」的限定，不写无条件事实；
② 每次发布前如果动了撤销或 UID 语义，至少重跑 Google 那一行；③ 新客户端（MIUI / 鸿蒙 /
iOS 原生）按同一列结构补行，**没验的格子写"未验"而不是留空或照抄别家**。

**本次演练里矩阵欠的两格**（顺手可得，下次动到相关面时补上）：

- **产物改名后，已订阅的客户端会不会跟着改显示名**。矩阵里那一列记的是「添加那一刻」
  的行为（Google 网页 / ColorOS 采用 `X-WR-CALNAME`，Outlook 忽略），而 10-11 下午
  日常产物补上年级后缀之后，**已经添加好的**日历会不会自己变成新名字，没有读数。
  这是一次白捡的观测：下次任何客户端的日历名发生变化时记一笔即可。
- **Outlook.com 在订阅源 404 之后的处置**（是清掉整个日历还是留着残条）。
  演练产物已从分支移除、URL 已 404，Google 那一腿因为用户删掉了订阅而作废，
  只剩 Outlook 这一条还挂着。

## 6. 发布通路的可操作性：`login` 的三处静默失败（v0.6.1 候选，纯本机体验）—— **提示层已落地（2026-10-11）**

**落地范围（commit `6b15f63`）**：三处全部改成会自己说清楚——沿用旧会话时打印
「沿用本地会话（**未验证有效性**）」并直接给出 `login --force` 出口、`cmd_login` 不再说
「会话就绪」、401 与"一个 cookie 都没抓到"两条提示都点名 `--force`、说明里写明这是
【独立的浏览器实例】且这一步要真人完成、中止时补「会话未保存」。
**没有落地的部分**：下面第 1 条提的"廉价会话有效性探测"——它要新增一次网络请求，
而"探测不通"和"会话过期"必须可区分（与 v0.5 三态判定同一个保守原则），风险大于收益，
因此只做了文案层。**这条不是遗漏，是取舍。** 原文保留如下。

订阅通路要长期成立，前提是"每两周能顺利重登一次"。10-11 那次排障里，
`login` 有三处**看起来成功、其实什么都没做**的地方，每一处都足以让人误判方向：

1. **过期会话不触发重登**。只要 home 里存在会话文件，不带 `--force` 的 `login`
   就打印「已检测到本地会话」并退出，不看那份文件是几号的、`fetch` 是不是正在 401。
   **改动面**：`inspect_session` 已经知道 `_saved_at`，让它顺带做一次**廉价的会话有效性
   探测**（学期发现接口单发只读即可），过期时在提示里直接给出「请跑 `login --force`」；
   或者干脆让 `fetch` 撞 401 时把这句建议打在错误出口上（现在只报 401）。
2. **交互式流程无法从后台执行器完成**。它停在终端等一个 Enter，管道里等不到，
   表现是"卡住"，还会留一个占住 profile 目录的浏览器窗口。
   **改动面**：`--timeout` 之类没有意义（要的是真人），能做的是把"请在自己的终端里运行"
   这句话写进交互提示的第一行，并在被 `EOFError` 中止时明确说明"会话未保存"。
3. **"我在浏览器里登录了"与工具会话互不相通**。工具用的是独立用户数据目录，
   用户平时浏览器里的登录态对它毫无作用。这一点 README 已经补了，
   但窗口标题 / 终端提示里最好也带一句「这是独立浏览器实例，请在**本窗口**内登录」。

**代价**：都是提示与判据层面的改动，不动数据通路、不动产物字节。
第 1 条要新增一次网络探测，得保证它失败时**不**把"探测不通"误报成"会话过期"
（与 §7 三态判定同一个保守原则）。

## 7. 托管：GitHub Pages 在免费账户上的硬门槛（决策类，不是代码类）

第 4 条那个"公开分支能枚举 token"的问题，最省事的解法是把发布仓库转私有——
但**免费账户的 GitHub Pages 不能由私有仓库发布**，这是方案层面的死路，不是配置问题。
因此换托管（Cloudflare Pages 一类静态托管）是**零代码改动**的：工具只认 `url_base`，
发布路径本身是普通 git push 到一个只放一个 `.ics` 的分支，换远端就是换个 remote 和 URL。
唯一不能省的先决门槛是**手机关掉代理后能否打开新域名**——打不开就整条链路白换。
具体步骤与回滚记在 `_notes/migration-cloudflare-pages.md`（gitignored，不进仓库）。

## 8. 要不要给"已过原定时刻"的条目也发墓碑（**已回答：不发**，2026-10-13 实测）

**触发点**：2026-10-12 的整学期迁移演练。v1 的 96 条里有 **21 条原定时刻已过**，被 CD10 的
过期筛放掉 ⇒ 它们既不进 live、也不进墓碑，从产物里**彻底消失**。

- **ColorOS（10-12 整学期演练）**：这 21 条在「删除日历 + 重新添加」之后**仍在**手机上

## 9. 门户首页那张「我的课表」卡片点不动（2026-10-14 记为已知卡点，未取证）

§6 的三处静默失败都已修（提示层 `6b15f63`、判据 0.8.2、自检 0.8.4），但 0.8.4 只让
"登录没走完"**看得见**，没解决**为什么走不完**。当天 16:4x 的真人登录给出了一条新证据，
和此前所有文档写的都不一样：用户**已经过了「请选择身份」**（门户首页带着
`JSESSIONID`、`route`、`CASTGC` 三条门户 cookie），卡的是首页上「我的课表」那张卡片
——"根本点不了，直接卡住"。所以说明第 2 步"点「学生」再进我的课表"只覆盖了一半场景。

最后那 4 条 `/jwapp` cookie 是怎么到手的**未取证**（用户当时没细看，事后也没复现）。
在此之前不要把这条当已解决的 bug 写进任何用户文档。

**两条待查（都要真人前台配合：profile 一次只能被一个浏览器实例占住）**

1. 那张卡片是不是 `window.open` 开**新标签**。若是，`login` 的轮询读的是
   `context.cookies()`（整个上下文，跨标签都能看到），但用户盯着的"卡住"是老标签的画面
   ⇒ 体验上永远像没反应。**判据**：登录后在窗口里按 `Ctrl-T` 看标签数，或直接看地址栏变没变。
2. 应用裸地址 `/jwapp/sys/wdkb/*default/index.do`（**不带** AMP 的 `gid_` /
   `amp_sec_version_` 参数）能不能直达。**判据**：headless 重放时 `goto` 那个裸地址，
   看落地是课表还是金智异常页。若能直达，就把"按完 Enter 自动 `goto` 课表页"做进 `login`
   ——用户从此不必点那张卡片，这一节和 §6 一起作废。

**为什么先记不修**：两次取证机会都要求用户空出 profile、重跑一次前台登录，
而 16:46 那次已经可用、`fetch`/`doctor`/`diff` 全绿。为一条"未复现的 UI 卡点"再占用户
一次登录，收益不划算。下次**因为别的原因**要他重登时顺手带上这两个观察点即可。
